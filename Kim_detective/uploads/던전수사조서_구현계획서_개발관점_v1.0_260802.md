## 2. 아키텍처

### 2.1 5계층 아키텍처 [상속: 참고 1 §3]

의존성은 아래에서 위로 단방향이며, 상위 계층은 하위 계층을 직접 참조할 수 없다.

```text
5. UI·연출 계층      Presentation      PublicDTO만 수신. 공개 정보만 표시
4. AI 표현 계층      DialogueRenderer  allowed_claims/reaction_key만 수신. 결정된 것을 연기
3. 게임 규칙 계층    GameRule Engine   자원·카드·판정·기믹·승패
2. 지식 상태 계층    KnowledgeState    플레이어가 아는 것 (진실이 아님)
1. 사건 논리 계층    TruthGraph        실제 진실. 런타임 읽기 전용
```

**의존성 규칙 R-1~R-6** [상속: 참고 1 §3.1.1] — 전문을 규칙으로 채택하고, dependency-cruiser 설정과 아키텍처 테스트(§12.3)로 강제한다.

1. TruthGraph는 어떤 계층도 참조하지 않는다 (순수 데이터)
2. KnowledgeState는 TruthGraph를 읽되 쓰지 못한다
3. GameRule은 1·2를 읽고 2를 쓴다. 1은 쓰지 않는다
4. DialogueRenderer는 엔진이 전달한 허용 목록만 받는다. TruthGraph 직접 접근 불가
5. Presentation은 PublicDTO만 받는다
6. **어떤 계층도 사건 ID·용의자 ID·증거 ID를 코드 상수로 갖지 않는다** — RQ-1의 코드 수준 표현. CI에서 리터럴 탐지로 검사(§12.3)

### 2.2 아키텍처 3원칙 (전 모듈 공통)

1. **엔진이 심판, AI는 배우** [상속: 기획 §7.1, 참고 1 §3.5] — 판정·자원·승패에 AI 출력이 관여하는 코드 경로가 존재하지 않는다. AI 계층은 판정 완료 *후* 표현 단계에만 위치한다(§6.1 상태 머신). "AI on/off 판정 로그 동일"(기획 M4 게이트)은 이 구조의 자동 귀결이며, 테스트는 구조가 무너졌는지의 감시다.
2. **진실과 지식의 분리** [상속: 참고 1 §3.3] — 어떤 주장이 거짓이어도 플레이어가 증명하기 전에는 지식 상태가 `UNKNOWN`이다. `truth_relation`을 상태 축으로 복사하는 코드는 금지(불변식 I-5, §12.3에서 검사).
3. **화이트리스트 DTO** [상속: 참고 1 §19.1] — UI로 나가는 데이터는 "지우는" 방식이 아니라 "담는" 방식으로 만든다. 기획 §10.4 공정성 QA(방어막 외형 동일·정답 비노출)의 구조적 해답이며, 필드 누설은 LeakageTests(§12.4)가 정적으로 잡는다.

### 2.3 기획 확정 사항(D-1~D-7)의 구현 반영 [상속 + 결정]

기획 §3.2에서 확정된 7개 결정을 코드·데이터 구조로 번역한다. 이 표가 기획-개발 간 추적성(traceability)의 정본이다.

| 기획 결정 | 구현 방식 | 비고 |
|---|---|---|
| **D-1** 판정 내부 5종·표기 4종 | `ResolutionCode` 5종: `R_DIRECT_CONTRADICTION` / `R_INDIRECT_SUSPICION` / `R_INSUFFICIENT_GROUNDS` / `R_TRUTH_ATTACKED` / `R_IRRELEVANT_EVIDENCE` (+행동계 코드, §5.3). UI 매핑 테이블에서 `R_IRRELEVANT_EVIDENCE` → '불충분' 연출 + 전용 피드백 문구 키 | 참고 1 §14.7 F-1(합리적 불충분 vs 무관 구분)을 내부 코드로 유지 |
| **D-2** 6태그 고정 | `Facet` 열거형 6종: `WHO/WHEN/WHERE/WHAT/HOW/WHY`. 참고 1의 세부 Facet 16종 미도입. 단 **입증 범위 어휘 `ProofScope` 11종은 채택** [결정] — 근거: QA1(국밥집 영수증 함정)·QA12(다중 출처 교차)가 "태그는 맞지만 범위가 모자란" 판정을 요구하며, 이는 태그(주장 분류)와 별개인 범위(입증 어휘) 없이는 데이터로 표현할 수 없다. UI에는 scope를 그대로 노출하지 않고 한국어 피드백 문구로 번역한다(§5.4) | 참고 1 §11.6 |
| **D-3** COMMIT 미도입(클립 한정) | `COMMIT` Intent는 엔진에 존재하되 **기본 행동·기본 카드로 노출하지 않는다.** 클립 「진술 고정」 카드만 `intent: "COMMIT"`을 갖는다. COMMITTED 반박 배율(참고 1 §14.6, 계수 TBD)은 balance.json 키로 존재 | 엔진 어휘는 완전, 노출은 축소 — 사건 추가 시 코드 수정 0건 원칙과 정합 |
| **D-4** 증거 등급 A/B/C | `EvidenceState.grade` 저장 필드. 판정 반영 [결정]: **A 보정 없음 / B 포함 시 유효 최소 독립 출처를 2로 상향(하한 방식, 공식은 부록 B) / C는 충분성 상한 `PROVISIONAL`(단독으로 SUFFICIENT 불가)**. 근거: D-4 원문 "사본 B로 직접 모순 시 독립 증거 1개 추가 요구", "C는 보조 전용"을 판정 축(독립성·충분성)의 파라미터로 번역한 것. 참고 1 §11.7은 강도 저장 금지를 요구하나 이는 *진실 파생 강도*에 대한 것 — A/B/C는 원본성(무결성) 등급으로 진실값과 무관해 누설이 아니다 | 파쇄·소각에 의한 A→B 하락은 `grade` 갱신으로 구현 |
| **D-5** 강압 게이지 수치 | 전부 balance.json 키 (부록 C). 판정 코드별 기본 델타 + 도장·기믹 배율(고블린 반사 2배)이 곱해지는 순서를 §5.5에 고정 | |
| **D-6** 드로우·손패 | balance.json: `draw.initial=5, draw.perTurn=1, draw.handLimit=7, draw.reshuffleOnEmpty=true` [초안, 기획 권장 초안 그대로] | M0 확정 대상 |
| **D-7** 페이즈 = 라운드 해결 기반 | `FlowNode.enter_conditions`를 Claim 상태 조건으로 작성. 평정심 %는 조건이 아니라 **Trigger(`ON_COMPOSURE_THRESHOLD`)로만** 사용 (미노 돌진 예고·서큐버스 봉인 등) | 참고 1 §16 |

### 2.4 Claim 상태 3축 모델 — 채택 범위 [결정]

참고 1 §6은 Claim 상태를 발언(Commitment)·검증(Epistemic)·표시(Presentation) 3축으로 분리한다. 기획 O-6는 "참고 1 수준의 완전 일반화"를 해커톤 이후로 이관했으므로, 여기서 **3축 구조 자체는 채택하되 각 축의 값은 기준 콘텐츠가 실제로 요구하는 것만 사용**한다. 아래 표가 "과잉 일반화가 아니라 최소 구현"임의 증명이다 — 모든 값이 기준 콘텐츠의 확정 기능에 1:1 대응한다.

| 축 | 값 | 요구하는 기준 콘텐츠 기능 |
|---|---|---|
| Commitment | `UNSTATED` | 질문으로 열리는 미공개 주장 (질문 카드) |
| | `ASSERTED` | 일반 진술 |
| | `COMMITTED` | 클립 「진술 고정」 (D-3) |
| | `REVISED` | 보스 변명으로 말 바꾸기 (T-6 전이) |
| | `RETRACTED` | 사이클롭스 증언 철회 (F-11) |
| | `CONTRADICTED` | COMMITTED 후 상충 진술 → 자체 모순 |
| Epistemic | `UNKNOWN`→`SUSPECTED`→`REFUTED` | 간접 의심 → 직접 모순 진행 |
| | `PROVISIONAL`→`SUPPORTED` | 사실 확인 → 확정 사실 고정 (QA6) |
| | `UNRESOLVED` | 오크 파쇄로 경로 소실 (QA10) — 대체 증거 획득 시 복귀 가능 |
| Presentation | `NORMAL` / `HIDDEN` | 기본 표시 / 미공개 |
| | `COMPOUND` | 재질문(CLARIFY) 대상 복합 진술 |
| | `DISTORTED` | 드워프 블라인드 셔플 |
| | `LOCKED` | 물컹이 [누가] 잠금 (QA9) |
| | `DUPLICATED` | **사용 사건 없음 — enum 예약만** |

미채택(해커톤 이후): 16종 세부 Facet, COMMIT의 기본 행동화, `DUPLICATED` 활용 콘텐츠, EpistemicState 되돌림의 서사 장치([후속 확장], 참고 1 §6.3).

상태 불변식 I-1~I-5 [상속: 참고 1 §6.7]는 개발 빌드에서 assert로 강제한다. 특히 **I-3 (Presentation 변경은 다른 두 축을 절대 바꾸지 않는다)**이 "적 기믹이 추리를 되돌리지 않는다"(기획 §5.3 셀프 검수 항목)의 코드 표현이다.

### 2.5 타입으로 강제하는 경계 [상속: 참고 1 §8.3 + 결정]

- AI 모듈에는 `Claim`을 그대로 넘기지 않고 축소 뷰 `RenderableClaim { claim_id, canonical_meaning, facet }`만 넘긴다. `truth_relation`·`ProofRule`·`Hypothesis` 필드는 타입에 존재하지 않으므로 컴파일 수준에서 접근 불가.
- Presentation 모듈의 진입 타입은 `PublicDTO`뿐이다. 엔진 객체 import는 dependency-cruiser 규칙 위반으로 CI 실패.
- 개발자 콘솔(§10.4)의 truth 열람은 `import.meta.env.DEV` 분기 + 릴리스 번들에서 트리 셰이킹으로 물리 제거한다.

### 3.4 결정론 규칙 [상속: 참고 1 §20.5]

| 항목 | 규칙 | 구현 |
|---|---|---|
| 무작위 | 모든 무작위는 run_seed 파생 스트림 | `rng/` 자체 구현(예: mulberry32), 용도별 스트림 분리(덱 셔플·기믹 선택·AI 시드) |
| 순회 순서 | 해시 순회 금지 | 배열 + 정의 순서. Map 사용 시 정렬 후 순회를 헬퍼로 강제 |
| 부동소수점 | 신뢰도 비교는 epsilon 명시 | `approxGte(a, b, EPS)` 헬퍼만 사용 |
| 시각 | 엔진 로직에 실시간 시각 금지 | 애니메이션 시간은 ui/만 소유 |
| AI | 판정에 무영향 | §2.2 원칙 1, 검증은 §12.4 |

결정론의 산출물이 **판정 로그 리플레이**다: `(run_seed, 입력 시퀀스)`만 저장하면 어떤 버그도 재현된다. 같은 시드·입력으로 두 번 실행해 로그가 동일한지 확인하는 회귀 테스트를 CI에 둔다 [상속: 참고 1 §25.3 test_deterministic_replay].

## 4. 데이터 스키마

### 4.1 패키지 구성 [상속: 기획 §5.1]

**사건 3개 = 데이터 패키지 3개 + 공통 데이터 1벌.** 사건 패키지에 전투 로직을 넣지 않고, 공통 데이터에 사건 이름을 넣지 않는다. EP001은 M3에서 "데이터 추가만으로" 들어와야 하며(§15 게이트), 이 절의 스키마가 그 성립 조건이다.

### 4.2 사건 패키지 — case.json 최상위 [상속: 참고 1 §9.1, 해커톤 축소 명기]

```jsonc
{
  "schema_version": "1.0",
  "case_id": "case_tutorial",
  "metadata": { "title": "황금 엘릭서 믹스커피 절도", "act": 0, "estimated_turns": 8 },
  "entities": [],        // 인물·장소·물건 — Claim·Observation의 참조 대상
  "events": [],          // Truth Seed의 구조화 — 실제로 일어난 일
  "claims": [],          // §4.3
  "inquiry_routes": [],  // 질문 경로 — 무엇을 물으면 무엇이 열리는가
  "evidence": [],        // §4.4
  "proof_rules": [],     // §4.5
  "encounters": [],      // 전투별 초기 자원·라운드·기믹·목표·결과 (§4.6) — 사건당 3전투이므로 배열
  "events_noncombat": [],// 이벤트 씬 A/B/C 패턴 데이터 (§6.6)
  "flag_hooks": [],      // F-01~F-13의 발생·소비 선언 (§4.10)
  "dialogue": {}         // 화자 프로필 + 폴백 전량 (§4.8)
}
```

참고 1 대비 축소 [결정]: `hypotheses`는 최상위 배열로 두지 않고 ProofRule의 선택 필드로만 유지한다(참고 1 §12.7 MVP 열 — "대안 가설: 명시 목록 대조"). 간접 의심 판정은 대부분 scope 미포섭·partial_credit으로 표현 가능하다(부록 B QA4·QA7 도출 참조).

### 4.3 Claim 스키마

```jsonc
{
  "claim_id": "clm_t01_who",
  "speaker": "ent_slime",
  "facet": "WHO",                       // 6태그 고정 (D-2)
  "canonical_meaning": "사건 시간대 탕비실에는 자신 혼자 있었다",
  "predicate": "PRESENT_ALONE",         // required_scopes 기본값 생성용 (참고 1 §12.5)
  "time_ref": { "from": "17:00", "to": "17:30" },
  "initial": { "commitment": "ASSERTED", "presentation": "NORMAL" },
  "lock": {                              // 물컹이 잠금 등. 없으면 생략
    "locked_at_start": true,
    "unlock_conditions": [
      { "type": "PARTNER_SKILL", "skill_id": "skill_witness_notice" },
      { "type": "CONFIRMED_TRUTH_COUNT", "count": 2 }
    ]
  },
  "truth": { "relation": "CONTRADICTED_BY_WORLD", "contradicting_events": ["evt_minotaur_1720"] }
}
```

`truth` 블록은 TruthGraph 소유이며 DTO로 절대 나가지 않는다(§2.2 원칙 3). 방어막(내구·저항)은 Claim이 아니라 encounter의 라운드 정의에 속한다 — 같은 주장이 전투 연출에서 다른 내구를 가질 수 있고, 저항도가 진실값과 상관을 갖지 않도록 배치 검증(F-1, §12.4)의 대상이 되기 때문이다.

```jsonc
{
  "evidence_id": "ev_t05_delivery_slip",
  "title_key": "loc.ev.t05.title",
  "acquire": { "node": "T-02", "method": "EVENT_CHOICE" },
  "source_category": "DOCUMENT",        // 물리/디지털/증언/금융/문서 — 기획 부록 B. 최종 보스 교차 검증 입력
  "independence": { "source_id": "src_delivery_co", "group": "DOCUMENT", "derived_from": null },
  "grade": { "initial": "B", "upgrades": [ { "to": "A", "cost": { "dp": 15 }, "via": "FORENSIC_SEAL" } ] },
  "observations": [
    { "predicate": "RECORDED_AT_TIME", "summary_key": "loc.ev.t05.obs1",
      "scopes": ["ACTION"], "detail": { "ordered": 3, "received": 2 }, "confidence": 0.9 }
  ],
  "not_proven_keys": ["loc.ev.t05.np1"]   // "반출자는 특정하지 못한다" — 조서 UI 필수 표기 (기획 §5.3)
}
```

- `observations[].scopes`가 판정의 핵심 어휘다(§5.2). `not_proven`은 게임 텍스트이자 기획 셀프 검수 산출물("입증하지 못하는 것 1문장")을 데이터로 강제하는 자리다.
- `grade`는 D-4의 저장 등급. 파쇄·소각은 `EvidenceState.grade` 하락 + `integrity` 변경으로 반영한다.
- 독립성 3필드(source_id/group/derived_from) [상속: 참고 1 §11.8]. **`group`에 출처 분류 5종을 사용** [결정] — 기획 부록 B가 "출처 분류는 최종 보스 3출처 교차 검증의 입력"이라 명시했으므로, 별도 개념을 만들지 않고 독립성 그룹으로 재사용한다. 최종 보스 필수 주장의 ProofRule에 `minimum_independent_sources: 3`을 걸면 교차 검증 규칙이 데이터만으로 성립한다.

### 4.5 ProofRule 스키마 [상속: 참고 1 §12.3 혼합형]

```jsonc
{
  "rule_id": "pr_e401_where_contradict",
  "target_claim_id": "clm_e401_where",
  "direction": "CONTRADICT",
  "requirements": {
    "required_scopes": ["IDENTITY", "TIME", "LOCATION"],
    "minimum_confidence": 0.9,
    "minimum_independent_sources": 1,
    "require_integrity": true
  },
  "guaranteed_evidence_sets": [ ["ev_e402_gate_log"], ["ev_e403_esign"] ],
  "known_insufficient_sets": [ ["ev_e401_soup_receipt"] ],   // 함정 교보재의 명시 등록 (튜토리얼 유도)
  "partial_credit": { "scopes_covered_ratio": 0.5, "result": "SUSPECTED" }
}
```

혼합형의 의미: `guaranteed_evidence_sets`(기획자가 검증한 성공 조합)가 우선 매칭되고, 등재되지 않은 제출은 의미 기반 조건(required_scopes·confidence·독립성)으로 평가한다. 이것이 참고 1 §14.7 F-5("기획자가 예상 못 한 타당한 조합도 인정")의 데이터 구조다. 평가 알고리즘은 참고 1 §12.6을 그대로 채택한다(§5.2).

### 4.6 Encounter 스키마 (전투 1개)

```jsonc
{
  "encounter_id": "enc_t01_slime",
  "target_entity": "ent_slime",
  "resources": { "composure_max": 60, "cp_per_turn": 3, "cp_max": 3,
                 "coercion_limit": 100, "shields_per_round": 2 },
  "rounds": [ { "round_id": "r1", "statement_claims": ["clm_t01_who", "clm_t01_when", "..."],
                "shields": [ { "claim_id": "clm_t01_who", "durability": "TBD" } ] } ],
  "flow_nodes": [],        // §6.5 — 보스 페이즈 전이 (D-7: 라운드 해결 기반)
  "modifiers": [],         // §6.4 — 기믹 Trigger·Condition·Effect
  "objectives": { "required": [], "optional": [], "state_conditions": { "composure_min": 1, "composure_max": 30 } },
  "outcomes": []           // §6.3 — BEST / PARTIAL / COERCED / FAILED 조건과 보상·플래그
}
```

전투별 초기 수치의 출처(기준 2 각 전투 시트): 평정심 — 물컹이 60 / 하피 70 / 미노타우로스 120 / 고블린 90 / 오크 100 / 서큐버스 140 / 드워프 110 / 사이클롭스 120(최대 CP 2) / 타락한 용사 180. CP는 턴 시작 3 회복(기준 2 §2.1 턴 구조), 최종 변호인 구간 강압 한계 40%(기준 2). 이 값들은 case 데이터에 초기값으로 기록하되, 기획 §6.3이 재검증 대상으로 지정한 항목(보스 평정심 등)은 balance.json 오버라이드 키를 허용한다(§4.9).

### 4.7 공통 데이터 — cards.json (14종) [상속: 기획 부록 C + 참고 1 §13]

카드는 클래스가 아니라 **Intent + 비용 + 대상 조건 + Modifier 데이터**다(참고 1 §13.1 카드별 클래스 금지). 기획 부록 C 14종의 Intent 매핑:

| 카드 | Intent | 비고 |
|---|---|---|
| 탐문 질문 ×2 | `QUERY` | 대상: QuestionRoute |
| 재질문 ×2 | `CLARIFY` | 복합 토큰 분해·교란 복구 + 불일치 가능성 표시 |
| 사실 확인 ×2 | `CONFIRM` | 지지 증거 첨부 → 진실(함정) 방어막 제거 |
| 모순 지적 ×2 | `CONTRADICT` | 피해 기본 18 (기준 2 확정) |
| 심호흡 ×1 / 완급 조절 ×1 | `RECOVER` | 자원 회복·피해 감쇄 |
| 압박 | `PRESSURE` | 성장 보상 |
| 현장 감식(임시) / 감식 계열 | `FORENSIC` | T05 등급 승급, 증거 상세 공개 |
| 절차 고지 · 이중 장부 · 물증 대조 · 공익 수사 | `SPECIAL` | `special_effect_id`로 공통 Effect 조합 참조 — 자유 스크립트 금지 [상속: 참고 1 §13.3 SPECIAL] |
| 진술 고정 (클립) | `COMMIT` | D-3 한정 구현 |
| 연속 추궁 (클립) | `CLARIFY`+`CONTRADICT` 연쇄 | `chain` 필드로 2단 제출 [결정] — 신규 Intent를 만들지 않고 기존 Intent 순차 실행으로 표현 (참고 1 §7.6 Q2) |

미구현 Intent [결정]: `CROSS_CHECK`는 enum에 예약만 한다. 근거: 초기 덱 6종·특수 8종 어디에도 매핑 카드가 없고(기획 부록 C·E), "말 바꾸기 → 자체 모순"은 FlowNode 전이 규칙 T-6이 자동 생성한다(§6.5). 최종 논고의 다중 출처 대조는 CONTRADICT + 다중 증거 첨부로 표현된다(QA12).

### 4.8 dialogue — 폴백 전량 [상속: 참고 1 §18.7]

```jsonc
{
  "speaker_profiles": { "ent_slime": { "race": "SLIME", "personality": ["TIMID"], "speech": "POLITE_TREMBLING",
                                        "forbidden_expressions": ["사실은", "거짓말"] } },
  "statements":  { "clm_t01_who": { "fallback": ["오후 5시에는 저 혼자 탕비실을 청소했어요…"],
                                     "spans": [ { "claim_id": "clm_t01_who", "start": 9, "end": 21 } ] } },
  "reactions":   { "reaction_insufficient_timid": ["그, 그게 무슨 증거가 되나요…?"] },
  "confession":  { "full": ["…"], "coerced": ["…"] }

```

폴백 계약 [상속]: 폴백은 AI와 동일한 claim_id·span 구조를 갖고, 사전 검증분이므로 런타임 재검증하지 않으며, 모든 Claim·ReactionKey는 폴백 최소 1개를 갖는다(검증 A-6, §10.2). 대사 260~410문장(기획 §6.2)이 이 파일들에 들어간다 — 사건당 1파일이 아니라 전투당 1파일로 분할해 M2~M3 작성 부하를 나눈다 [결정].

### 4.9 balance.json — 재빌드 없는 튜닝 [결정]

기획 §6.3 미정 수치 전체를 키로 보유한다(전체 카탈로그 부록 C). 로딩 규약: **번들 import가 아니라 런타임 fetch** — 파일 수정 + 새로고침이 곧 반영이며(RQ-5), M5 밸런싱은 이 파일과 case 데이터의 수치 필드만 만진다. case 데이터의 수치와 겹치는 항목(보스 평정심 등)은 `overrides.byEncounter` 키가 우선한다.

### 4.10 flags.json — F-01~F-13 [상속: 기획 부록 D]

플래그는 **발생(set)과 소비(consume)를 모두 데이터로 선언**한다. 소비는 encounter 로드 시점에 적용되는 훅이다:

```jsonc
{ "flag_id": "F-05", "set_by": [ { "encounter": "enc_t01_slime", "outcome": "COERCED_CONFESSION" },
                                  { "encounter": "enc_t03_harpy", "outcome": "COERCED_CONFESSION" } ],
  "consumed_by": [ { "encounter": "enc_t05_minotaur",
                     "apply": { "type": "MODIFY_SHIELDS", "delta": 1 } } ] }
```

이 구조 덕에 "허위 자백 → 보스 방어막 +1" 같은 연계가 엔진 분기 없이 성립하고, 13종 × on/off 연계 QA(기획 §10.3)를 시뮬레이터가 자동 순회할 수 있다(§10.3).

### 4.11 세이브 스키마 (§9.1에서 상세) — 상태 객체만 저장 [상속: 참고 1 §4.3]

정의 객체(CaseDefinition 등)는 저장하지 않고 `case_id + content_version`만 저장한다. 저장 대상은 런타임 상태(ClaimState·EvidenceState·DeckState·FlagStore·자원·run_seed)뿐이다.

### 4.12 Zod = 스키마 단일 원천 [결정]

모든 스키마는 `content-io/schemas/*.ts`의 Zod 정의가 정본이고, TS 타입은 `z.infer`로 파생한다. 동일 정의가 ① 빌드 시 콘텐츠 검증(§10.2 Tier 1) ② 개발 런타임 로드 검증 ③ 에디터 자동완성(JSON Schema 내보내기 → `$schema` 연결)에 재사용된다. 스키마와 타입이 어긋나는 사고를 원천 차단하는 것이 목적이다.

## 5. 판정 엔진 (Argument Resolver)

이 게임의 심장이다. 기획 §10.1 판정 QA 12케이스가 이 절의 수용 기준이며, 12케이스 각각이 어떤 축 값으로 도출되는지를 부록 B에 전수 기재했다.

### 5.1 판정 순서 10단계 [상속: 참고 1 §14.2]

```text
1  행동·대상 호환          → Validity        (INVALID면 즉시 종료, CP 미소비)
2  대상 공개 여부           → Validity
3  근거·주장 관련성         → Relevance       (NONE이면 4~8 생략, R_IRRELEVANT_EVIDENCE 확정)
4  지지·충돌 방향           → Relation
5  입증 범위 충족           → Sufficiency
6  신뢰도 기준              → Sufficiency
7  복합 증거 독립성          → Independence
8  대안 가설 제거            → (MVP 축소: ProofRule 명시 목록 대조만)
9  절차 적절성              → Procedure       (FORBIDDEN이면 R_PROCEDURE_VIOLATION)
10 조합표 조회 → 판정 코드 + 효과
```

### 5.2 판정 축 [상속: 참고 1 §14.3, MVP 범위 명기]

| 축 | 값 | 구현 |
|---|---|---|
| Validity | VALID / INVALID | 카드 target_filter × Claim 상태 대조. LOCKED 대상 처리(§5.6) |
| Relevance | NONE / PARTIAL / FULL | 제출 증거 observations의 scopes ∪ 와 대상 ProofRule required_scopes의 교집합 |
| Relation | SUPPORTS / CONTRADICTS / NEUTRAL / AMBIGUOUS | MVP: scope 집합 비교 + 시간 구간 충돌 검사(참고 1 §12.8 timeConflicts — 구간 겹침 + TRAVEL_TIME_MIN 결합) + 동일 ID 비교. 의미 추론 없음 (참고 1 §12.7 MVP 열) |
| Sufficiency | INSUFFICIENT / PROVISIONAL / SUFFICIENT | 참고 1 §12.6 evaluateProof 알고리즘 그대로: guaranteed set 우선 → known_insufficient → 의미 기반 → partial_credit |
| Independence | MET / UNMET | source_id·group·derived_from 3필드 기반 산출(참고 1 §11.8). **B등급 포함 시 유효 최소 독립 출처 하한 2 (D-4, 부록 B 공식)** |
| Procedure | FAIR / COERCIVE / FORBIDDEN | 변호인 페이즈의 빨간 도장 = FORBIDDEN (QA11) 등, 기믹이 조건 주입 |

### 5.3 판정 코드와 조합표 [상속: 참고 1 §14.4 → D-1 축소판]

증거 판정 5종(D-1 내부 분류) + 행동계 코드. 조합표는 참고 1 §14.4에서 **해커톤 채택 Intent 행만** 가져온다:

| Intent | 관련성 | 관계 | 충분성 | 독립 | 판정 코드 | 화면 표기 (D-1) |
|---|---|---|---|---|---|---|
| CONTRADICT | FULL | CONTRADICTS | SUFFICIENT | MET | `R_DIRECT_CONTRADICTION` | 직접 모순 |
| CONTRADICT | FULL | CONTRADICTS | SUFFICIENT | UNMET | `R_INDIRECT_SUSPICION` | 간접 의심 |
| CONTRADICT | FULL | CONTRADICTS | PROVISIONAL | — | `R_INDIRECT_SUSPICION` | 간접 의심 |
| CONTRADICT | PARTIAL | CONTRADICTS·AMBIGUOUS | INSUFFICIENT | — | `R_INSUFFICIENT_GROUNDS` | 불충분 |
| CONTRADICT | FULL | SUPPORTS | SUFFICIENT | — | `R_TRUTH_ATTACKED` | 진실 공격 |
| CONTRADICT | NONE | — | — | — | `R_IRRELEVANT_EVIDENCE` | 불충분(전용 문구) |
| CONFIRM | FULL | SUPPORTS | SUFFICIENT | MET | `R_CONFIRM_LOCKED` | 확인 성공 |
| CONFIRM | FULL | SUPPORTS | PROVISIONAL | — | `R_CONFIRM_PROVISIONAL` | 임시 확인 |
| CONFIRM | FULL | CONTRADICTS | SUFFICIENT | — | `R_CONFIRM_CONFLICT` | 확인 실패(모순 힌트) |
| QUERY / CLARIFY / COMMIT / PRESSURE / RECOVER / FORENSIC / SPECIAL | (참고 1 §14.4 해당 행 그대로) | | | | `R_QUERY_SUCCESS` 등 | |
| 전 Intent | Procedure=FORBIDDEN | — | — | — | `R_PROCEDURE_VIOLATION` | 변호인 개입 연출 |

구현 형태 [결정]: 조합표는 **코드 상수(타입 안전한 룩업 테이블)로 시작**하고, 데이터 파일 외부화는 M5 튜닝에서 필요가 확인될 때만 한다(참고 1 §14.4 말미의 [후속 확장] 지위 유지 — DEV-O-1). 단, **정의되지 않은 축 조합이 입력되면 조용한 기본값이 아니라 명시적 예외**를 던진다 [상속: 참고 1 §25.3 test_resolution_table_completeness]. 조합표 전 행 + 예외 경로가 단위 테스트 대상이다.

### 5.4 판정 코드별 효과 [상속: 참고 1 §14.5 관계 확정·수치 TBD]

| 코드 | 평정심 | 강압 | 상태 전이 | 추가 효과 |
|---|---|---|---|---|
| R_DIRECT_CONTRADICTION | `-balance.dmg.contradict` (기본 18, 기준 2) × 배율 | +0~2% | Epistemic → REFUTED | 방어막 파괴, 후속 공개, 페이즈 전이 검사 |
| R_INDIRECT_SUSPICION | 소량 (TBD) | +0~2% | → SUSPECTED | 방어막 균열, 후속 질문 경로 개방 |
| R_INSUFFICIENT_GROUNDS | 0 | +0~3% (D-5) | 유지 | **missing_scopes 피드백** (§5.5) |
| R_TRUTH_ATTACKED | 0 | +10~20% (D-5) | → PROVISIONAL | 저항 +1, 반발 리액션 |
| R_IRRELEVANT_EVIDENCE | 0 | +5~10% (TBD) | 유지 | 전용 피드백 "이 증거는 이 주장과 무관하다" (D-1) |
| R_CONFIRM_LOCKED | 0 | 0 (최종전 -3%, D-5) | → SUPPORTED | 함정(진실) 방어막 제거 + 사실 고정 (QA6) |
| R_PROCEDURE_VIOLATION | 0 | 즉시 패배 경로 (QA11) | 유지 | 변호인 연출 |

전 수치는 balance.json 키다(부록 C). 적용 순서 고정 [상속: 참고 1 §14.9]: **자원 → 상태 → 공개 → 카드 효과 → 기믹 → 목표 검사.** 순서가 바뀌면 같은 입력이 다른 결과를 낳는다.

### 5.5 실패 피드백 — 정답 비노출 [상속: 참고 1 §14.7 F-3]

```jsonc
{ "resolution_code": "R_INSUFFICIENT_GROUNDS",
  "feedback": { "covered_scopes": ["TIME", "LOCATION"], "missing_scopes": ["IDENTITY"] } }
```

`missing_scopes`는 공개하되 **어떤 증거가 그 범위를 채우는지는 공개하지 않는다.** UI는 scope 코드를 한국어 문구로 번역해 표기한다(judgment-ui-map.json): IDENTITY→"누구인지 특정되지 않았다", TIME→"사건 시간대를 포섭하지 못한다" 등. 이것이 기획 §10.4 "실패 피드백이 부족한 범위만 알려주고 정답 증거명을 노출하지 않는가"의 구현이다.

### 5.6 잠금(LOCKED) 처리 — QA9 [결정]

물컹이 [누가] 잠금: Claim `lock.locked_at_start` → PresentationState LOCKED. LOCKED 대상에 CONTRADICT 제출 시 Validity 단계에서 가로채 `R_ACTION_INVALID` 변형(`reason: "SILENCE"`)을 반환하고 묵비권 리액션 키를 재생한다(CP 소비 여부 TBD). 해제 조건(파트너 스킬 「계약직 신변 보호 고지」 또는 진실 태그 2개 CONFIRM 성공)은 KnowledgeState 카운터로 검사하며, 충족 시 LOCKED→NORMAL 전이 후 동일 제출이 정상 판정된다. 참고 1 §6.5 불변식 "LOCKED는 영구 잠금 불가 — 해제 수단 필수"를 스키마 검증(§10.2)에서 확인한다.

### 5.7 COMMITTED 배율 — 클립 「진술 고정」 [상속: 참고 1 §14.6, D-3 한정]

```text
if target.commitment == COMMITTED and code == R_DIRECT_CONTRADICTION:
    composure_delta *= balance.committedMultiplier   // 초안 1.4
```

## 6. 전투 런타임 — 상태 머신·자원·기믹·진행

### 6.1 전투 상태 머신 [상속: 참고 1 §20.3 + 기준 2 §2.1 턴 구조]

```text
ENCOUNTER_INIT → LOAD_CASE → (개발 빌드) VALIDATE → BUILD_TRUTH → INIT_KNOWLEDGE
→ ENTER_FLOW_NODE
→ RENDER_STATEMENT        ← AI 요청 → 검증 → (실패) 재시도 1회 → (실패) 폴백  ※ P0는 폴백 직행
→ EMIT_PUBLIC_DTO
→ TURN_START              ← CP 3 회복(기준 2), 드로우(D-6), 상태이상·쿨타임 틱
→ FREE_REVIEW             ← 조서·증거·이력 열람, 트레이 가설 연결 — CP 0, 상태 변경 0 (§6.2)
→ BUILD_ARGUMENT          ← 카드 + 태그 + 증거 첨부 선택
→ SUBMIT_ACTION → RESOLVE → APPLY_EFFECTS
→ RENDER_REACTION         ← ReactionKey → AI/폴백
→ RUN_MODIFIERS           ← 적 기믹 (§6.4)
→ CHECK_FLOW_TRANSITION   ← 페이즈 전이 (§6.5)
→ CHECK_OBJECTIVES → CHECK_OUTCOME
→ (반복) TURN_START | ENTER_FLOW_NODE | ENCOUNTER_COMPLETE
```

기준 2 §2.1의 8단계 턴(진술→태그 갱신→방어막→조서 확인→카드 선택→판정→적 대응→종료 체크)과 1:1 대응함을 M1 게이트에서 확인한다.

### 6.2 FREE_REVIEW 보장 [상속: 참고 1 §20.4]

이 단계의 모든 호출은 **순수 조회**다(엔진 상태 불변). 사건 조서 상시 열람(기획 R-4)이 비용 없이 성립하는 근거이자, "미리보기가 정답을 누설하지 않는다"의 구조적 보장이다. 공격 전 표시 가능 정보의 경계는 참고 1 §19.5 표를 그대로 채택한다(증거의 scope 목록·못 하는 것·비용은 표시 가능 / 정답 세트 여부·모순 확정 예측은 불가).

**Outcome 평가 순서** [상속: 참고 1 §17.6]: ① FAILED(스트레스 0/강압 초과/시간 초과/해결 경로 전무) 즉시 → ② COERCED(평정심 0) 즉시 → ③ 매 턴 종료 BEST 조건 검사 → 충족 시 **[진술 확보] 버튼 활성화만** → ④ 플레이어 선택으로 BEST 확정 → ⑤ 제한 턴 도달 시 PARTIAL. "조건 충족 ≠ 자동 종료, 플레이어의 명시적 선택"이 스위트 스팟 설계의 핵심이므로 ③④를 분리 구현한다. `NO_SOLVABLE_PATH`는 참고 1 §17.7 hasSolvablePath 알고리즘 채택 — 해결 불가 상태로 플레이를 지속시키는 것 자체가 불공정이기 때문(QA10의 반대면).

### 7.3 심문 화면의 구현 요점

- **타자기 스트리밍**: 진술을 글자 단위 출력 + 타건 SFX. 이 연출이 AI 생성 지연 은폐를 겸한다(기획 §8.6 "진술 스트리밍 은폐 겸용") — 스트리밍 응답을 받는 즉시 출력을 시작하고, 폴백 전환 시에도 동일 연출이라 플레이어가 차이를 느끼지 못한다.
- **방어막 동일 외형**: 위젯은 `PublicDTO.tokens[].resistance`(내구 수치)만 받는다. 내부 유형(모순/자신감/사생활)은 DTO에 존재하지 않으므로 **다르게 그릴 방법 자체가 없다** — 기획 §10.4 1항의 구조적 충족.
- **태그 칩 상태 4종**(기본/방어막/파훼/흔들림)은 ClaimState의 Epistemic·Presentation 조합에서 파생하는 표시 함수로 매핑. 파츠 오버레이 포트레이트는 베이스+파츠 좌표 JSON(§11.4).
- 판정·결말 연출 5종(기획 §8.5 매핑: 폴라로이드/송치 도장/BGM 뮤트/명함+노크/과로)은 ResolutionCode·OutcomeCode → 연출 키 테이블로 구동.

### 7.4 입력

마우스 단일 입력으로 완주 가능(카드 클릭→태그 클릭→증거 체크→제출). 키보드는 보조(스페이스 진행·숫자 카드 선택). QTE 2종만 타이밍 입력을 요구하며, 접근성·컷 대비로 `qte.autoSuccess` 데이터 스위치를 둔다(§6.4).

## 8. AI 통합 (P2)

### 8.1 Provider 구조와 키 보호 [결정]

```ts
interface DialogueProvider {
  renderStatement(req: StatementRequest): Promise<StatementResponse>;  // 진술 변주
  renderReaction(req: ReactionRequest): Promise<ReactionResponse>;     // 판정 리액션
}
// 구현체: ClaudeApiProvider(기본) / CacheProvider / FallbackProvider — 체인 구성
```

**브라우저에 API 키를 넣을 수 없다**는 실무 제약을 정면으로 다룬다. 순수 정적 배포본은 AI가 꺼진 P0 빌드(폴백 완주)이고, AI 시연은 다음 중 하나로 실행한다: ① Vite dev 서버 프록시(시연 머신 로컬 실행 — 권장) ② ~30줄 Node 사이드카 프록시 ③ 사전 생성 캐시 전용(네트워크 0). 심사 배포 링크는 P0 빌드 + 캐시 재생으로 안전하게, 라이브 변주는 발표 머신에서만. 최종 방식은 M4 진입 시 확정(DEV-O-3).

### 8.2 입출력 계약 [상속: 참고 1 §18.1~18.2 그대로]

입력: `speaker_profile`(금지 표현 포함) + `allowed_claims[]`(RenderableClaim — id·canonical_meaning·facet만) + `presentation_groups`(복합 토큰 지시) + `forbidden_information` + `seed`. 출력: `full_text` + `tokens[]`(claim_ids·span). 리액션 요청은 `reaction_key` + `missing_scopes` + `composure_band`(HIGH/MID/LOW/CRITICAL — 정확 수치 전달 금지: "이제 거의 무너졌다" 류 상태 누설 방지) [상속: 참고 1 §18.4].

### 8.3 출력 검증 파이프라인 [상속: 참고 1 §18.5, MVP 축소 §18.6]

```text
1 JSON 스키마(Zod) → 2 claim_id 전량 매핑 → 3 원자성(토큰당 1주장, presentation_groups 예외)
→ 4 span 정합(본문 일치·비중첩) → 5 허용 정보(사건 외 Entity 사전 대조 + 시각 표현 범위 검사
   + 토큰 밖 텍스트 길이 임계) → 6 금지 표현(정답 암시 어휘) → 7 문체 균질성(샘플링, WARNING)
→ 실패 시 재시도 1회 → 재실패 시 동일 claim_id 폴백 (게임 무정지)
```

기획 §7.3의 "span 6태그 1:1 실패 → 즉시 폴백"이 3·4단계다. 검증 실패율 10% 초과 시 검증기를 늦추지 않고 프롬프트를 고친다(기획 §7.3) — 실패율은 §8.5 로그로 상시 집계된다.

### 8.4 캐시와 재현성 [상속: 참고 1 §18.8 + 기획 §7.4]

생성마다 `request_id·seed·claim_ids·prompt_version·model_id·검증 결과·fallback_used·content_hash`를 기록한다. `content_hash` 동일 시 캐시 재사용. **시연 핵심 구간(물컹이 완전 진술·미노타우로스 자백·최종 논고)은 사전 생성→검증 통과분을 `content/ai-cache/`에 저장해 재생**하고, 라이브 생성은 일반 라운드에서만 — "AI 게임으로 보임"과 "시연 무중단"의 동시 충족(기획 §7.4).

### 8.5 M4 게이트의 측정 방법

- **AI on/off 판정 로그 동일**: 같은 seed·입력 시퀀스로 2회 자동 플레이(§10.3) → JudgmentLog 비교(diff=0). 아키텍처상 실패할 수 없어야 정상이며(§2.2 원칙 1), 이 테스트는 회귀 감시다.
- **검증 실패율 <10%**: 생성 로그의 `fallback_used` 비율 집계 리포트를 개발자 콘솔·CI 아티팩트로 출력.

### 9.3 설정

볼륨(BGM/SFX) · 화면 배율 · 타자 속도 · **AI on/off 토글**(P2 빌드에서도 런타임 차단 가능 — 시연 안전) · QTE 자동 성공(접근성).

모든 판정을 `{turn, input(카드·태그·증거), 축 값 5종, code, deltas}`로 기록. 용도: ① M4 on/off 동일성 ② 버그 리플레이(§3.4) ③ M5 밸런스 관측(§10.6 지표 — 턴 수·강압 패배율·스위트 스팟 이탈률을 로그 집계로 산출) ④ 개발자 콘솔 뷰어.

## 10. 콘텐츠 파이프라인·개발 도구

### 10.1 시트 → JSON 워크플로 [결정]

기획 산출물(전투 시트 9종, 부록 A 양식)은 문서로 작성하고, 데이터는 **JSON 직접 작성 + Zod 스키마 자동완성**($schema 연결)으로 전사한다. 전용 시트 변환기는 만들지 않는다 — 근거: 1인 개발에서 도구는 "2회 이상 반복되는 작업"에만 투자한다(§16 DR-7). 사건 3개 분량의 전사는 변환기 제작·유지 비용보다 싸고, 대사만 물량이 크므로 dialogue 파일 분할(§4.8)로 대응한다.

### 10.2 콘텐츠 검증기 — tools/validate [상속: 참고 1 §24 → 기획 §11의 최소 채택 + 단계 확장]

기획 §11은 "여유 시 참조 무결성·도달 가능성 2종만 스크립트화"를 지시했다. 개발 관점에서는 **Zod 도입으로 스키마 계열 검사가 사실상 무료**이므로, 다음 3티어로 실비용을 명시해 채택 범위를 확정한다:

| 티어 | 규칙 | 시점 | 비용 평가 |
|---|---|---|---|
| T1 (M0, 필수) | Zod 스키마 전량 + **L-7 참조 무결성**(모든 ID 참조 유효) + 잠금 해제 수단 존재(§5.6) | 빌드·로드 시 | Zod 정의의 부산물 — 추가 비용 극소 |
| T2 (M1~M2, 필수) | **L-1**(필수 Claim에 ProofRule 존재) · **L-2**(참조 증거가 획득 경로에 존재) · **L-3/P-1**(질문 경로·FlowNode 도달 가능) · **P-3**(파쇄·소각 최악 시나리오 후 해결 경로 생존 — QA10의 자동화) · **P-6**(경로 그래프 무순환) | CI + 로드 시(개발) | 그래프 순회 각 수십 줄. 기획이 지목한 "진행 불가·도달 불가"를 직접 방어 |
| T3 (M3~M4, 채택) | **L-4**(보장 조합이 실제 scope 요구 충족) · **F-1**(저항도-진실 상관 \|r\|>0.5 검출) · **F-2**(진실/거짓 DTO 필드 구조 동일) · **A-1~A-7**(AI 계약) | CI | F-1·F-2는 §12.4 LeakageTests로 구현(수십 줄). A계열은 §8.3 파이프라인의 테스트화 |
| 미채택(체크리스트로) | L-5·L-8·P-2·P-4·P-5·F-3~F-6 | 기획 §10 수동 QA | 자동화 비용 대비 사건 3개 규모에서 수동 확인이 저렴 |

실패 처리 [상속: 참고 1 §24.5]: ERROR = 빌드 실패/로드 거부(개발)/노드 스킵+로그(릴리스). 릴리스는 사전 검증본을 신뢰하고 재검증하지 않는다(기획 요약 §11 항목).

### 10.3 자동 플레이 시뮬레이터 — tools/simulate

엔진이 헤드리스(RQ-7)이므로 Node에서 그대로 구동한다. 전투 시트의 "대체 경로" 열을 **정책 스크립트**(카드·태그·증거 제출 시퀀스)로 전사해 실행한다.

- 최단 경로 정책 → BEST_RESOLUTION 도달 확인 (참고 1 §24.6 "가장 강력한 검증")
- 정책 변형(강압 유도·부분 종료) → **27셀 매트릭스**(9전투×3분기) 자동 채움 → 기획 §10.2의 실플레이 확인을 "자동 1차 + 수동 확정"으로 단축
- 플래그 13종 on/off 분기 로드 → 26개 시나리오 스모크 (기획 §10.3의 자동 1차)
- CI 예산: 전투당 <1초(순수 함수 판정이므로 충분) — 전체 5분 내

### 10.4 개발자 콘솔 (개발 빌드 전용, 백틱 토글)

truth 오버레이(태그 내부 판정 표시 — **릴리스 번들에서 물리 제거**, §2.5) / 자원 치트 / 노드 점프 / 강압·평정심 수동 조작 / AI on/off / 판정 로그 뷰어 / 플래그 뷰어·토글 / QA 12케이스 인게임 재생. 기획 §10.1 회귀("시트 수정 때마다")를 게임 안에서 1분 내 돌릴 수 있게 하는 것이 목적이다.

### 10.5 플레이스홀더 생성기 — tools/placeholder

실루엣+명패 규격(기획 §8.3)의 PNG를 캐릭터 목록에서 일괄 생성. M1에서 규격을 확정해 **애셋 미완이 빌드를 막지 않는 상태**를 M1~M5 내내 유지한다.

## 11. 애셋 파이프라인 (기술 측면) [상속: 기획 §8, 참고 2]

### 11.1 포맷·명명 규칙과 로더

- PNG(인덱스드 팔레트 권장), 명명 `카테고리_이름_상태.png` [상속: 참고 2] — **로더가 파일명을 파싱해 카테고리·상태 레지스트리를 자동 구성**한다 [결정]. 별도 매니페스트 수기 관리 제거.
- 상태 변형은 스프라이트시트 1장 통합(참고 2) → 프레임 격자 규격을 카테고리별 JSON 1개로 선언.
- 포트레이트 파츠: 베이스 1 + 파츠(눈썹·땀·입) 오버레이 좌표 JSON — `portrait_물컹이_base.png` + `portrait_물컹이_parts.png` + `portrait_물컹이.parts.json`.

### 11.2 팔레트 검증 — tools/palette-check [결정]

씬 구성 애셋의 사용 색상 수를 집계해 **16색/씬 초과 시 CI 실패.** AI 아트 파이프라인 4단계(생성→도트화→16색 리매핑→리터치, 참고 2)의 마지막 안전망이며, "16색 강제가 곧 스타일 통일 장치"라는 참고 2의 논리를 도구로 보증한다. 리매핑 자체는 이미지 도구(외부)에서 수행하고 이 스크립트는 검증만 한다.

### 11.3 아틀라스·로딩

이미지 총량 약 60점(기획 §8.7)이므로 전체 프리로드가 가능한 규모다(수 MB). 에피소드 단위 프리로드 + 로딩 화면 1종. 아틀라스 패킹은 무료 CLI(자체 스크립트 또는 free-tex-packer)로 M3에 도입하되, 그 전까지는 개별 PNG 로드로 충분하다 [결정 — 조기 최적화 회피].

### 11.4 오디오

SFX 12종 + BGM 4곡 + 스팅어 2(기획 §8.6). 포맷 OGG 단일 [결정 — 시연 브라우저 Chrome 고정, §1.3]. howler로 BGM 루프 포인트·강제 자백 시 **BGM 뮤트 연출**(기획 §8.5) 제어. FM 음원 제작(YM2203 계열 질감)은 애셋 제작 영역이며 런타임은 파일 재생만 담당한다.

### 12.3 일반화 회귀 [상속: 참고 1 §25.3]

- `test_deterministic_replay`: 동일 시드·입력 2회 실행 → 판정 로그 바이트 동일.
- 상태 불변식 I-1~I-5 assert (개발 빌드).

### 12.4 LeakageTests 구현 노트

진실 Claim과 거짓 Claim 쌍의 PublicDTO를 직렬화해 **필드 집합 동일성**을 비교(F-2)하고, 금지 필드 목록(truth_relation·proof_rules·is_lie 등, 참고 1 §19.2)의 부재를 키 순회로 확인한다. 저항도-진실 상관(F-1)은 사건 데이터 전 Claim에 대한 피어슨 r 계산 — 임계 \|r\|>0.5 ERROR. 참고 1 §19.4의 연출 누설 항목(테두리·속도·지연 등)은 자동화가 어려워 수동 체크리스트로 남긴다(§10.2 미채택 사유와 동일 논리).

## 부록 A. 핵심 타입 정의 (TypeScript 스케치)

전체 정의는 M0 스키마 동결 산출물이다. 여기서는 계약의 뼈대만 적는다.

```ts
// engine/domain — 읽기 전용 정의 객체
type Facet = 'WHO'|'WHEN'|'WHERE'|'WHAT'|'HOW'|'WHY';                       // D-2
type ProofScope = 'IDENTITY'|'TIME'|'LOCATION'|'PRESENCE'|'OWNERSHIP'|'ACTION'
                |'SEQUENCE'|'ROUTE'|'INSTRUCTION'|'MOTIVE'|'INTEGRITY';      // 참고 1 §11.6
type Grade = 'A'|'B'|'C';                                                    // D-4

interface Claim { claimId: string; speaker: EntityId; facet: Facet;
  canonicalMeaning: string; predicate: string; timeRef?: TimeRange;
  initial: { commitment: CommitmentState; presentation: PresentationState };
  lock?: LockSpec; }
// truth 블록은 TruthGraph 전용 타입에만 존재 — Claim 공개 타입에는 없음 (I-5)

interface Evidence { evidenceId: string; sourceCategory: SourceCategory;
  independence: { sourceId: string; group: string; derivedFrom: string|null };
  observations: Observation[]; notProvenKeys: string[]; gradeInitial: Grade; }

interface ProofRule { ruleId: string; targetClaimId: string;
  direction: 'SUPPORT'|'CONTRADICT';
  requirements: { requiredScopes: ProofScope[]; minimumConfidence: number;
                  minimumIndependentSources: number; requireIntegrity?: boolean };
  guaranteedEvidenceSets?: string[][]; knownInsufficientSets?: string[][];
  partialCredit?: { scopesCoveredRatio: number; result: 'SUSPECTED' }; }

// engine/knowledge — 런타임 상태 (세이브 대상)
type CommitmentState = 'UNSTATED'|'ASSERTED'|'COMMITTED'|'REVISED'|'RETRACTED'|'CONTRADICTED';
type EpistemicState  = 'UNKNOWN'|'SUSPECTED'|'PROVISIONAL'|'SUPPORTED'|'REFUTED'|'UNRESOLVED';
type PresentationState = 'NORMAL'|'COMPOUND'|'DISTORTED'|'HIDDEN'|'LOCKED'|'DUPLICATED';

// engine/resolution
interface ResolutionInput { intent: ActionIntent; target: TargetRef;
  evidenceSet: string[]; cardModifiers: MergedModifiers;
  knowledge: KnowledgeSnapshot; encounter: EncounterSnapshot; resources: ResourceSnapshot; }
interface Resolution { code: ResolutionCode;
  axes: { relevance: Relevance; relation: Relation; sufficiency: Sufficiency;
          independence: 'MET'|'UNMET'; procedure: Procedure };
  feedback?: { coveredScopes: ProofScope[]; missingScopes: ProofScope[] };
  reveals: string[]; reactionKey: string; }

// ai — 축소 뷰만 수신 (§2.5)
interface RenderableClaim { claimId: string; canonicalMeaning: string; facet: Facet; }

// dto — UI 유일 입력. truth 계열 필드가 타입에 존재하지 않음
interface PublicDTO { statement: TokenView[]; evidence: EvidenceView[];
  resources: ResourceView; objectives: ObjectiveView[]; enemyIntent?: IntentView; }
```
