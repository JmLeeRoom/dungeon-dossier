### 1.2 현재 게임의 실제 실행 구조

현재 심문 런타임은 아래 경계를 갖는다.

```text
JSON 콘텐츠/스키마
  → bootstrap 및 createEncounterSession
  → EncounterCoordinator / ResourceSystem / ArgumentResolver / OutcomeEvaluator
  → InterrogationScreenModel
  → Pixi 화면(createInterrogationScreen, cardWidget, gauge)
  → RunState / NodeStrip / 보상·저장
```

이 구조에는 CP 복원, 평정심·강압 판정, 육하원칙 태그, 스위트 스팟, 카드 합성 자산 등 v2의 기반이 이미 있다. 그러나 요구사항의 핵심인 **Submit 1회당 원자적 턴 소모**, **기본 5종 복원추출**, **방어막과 정오답 판정의 결합**, **카드 인스턴스별 3단계 강화**, **결정적 증거 기반 인과율 분기**는 아직 연결되지 않았다.

### 1.3 핵심 결론

1. **브랜딩은 대부분 교체됐지만 실제 타이틀 흐름은 미연결이다.** 메인 HTML, 프로젝트 workbench, README, 브라우저 preview 기대값과 `createTitleScreen`은 새 제목이다. 그러나 루트 legacy workbench와 일부 설계 문서에는 구 제목이 남고, Pixi 타이틀 화면은 bootstrap에서 호출되지 않는다.
2. **신규 PNG의 반입과 HUD 적용은 병행 구현됐다.** coffee·CP active/deactive·HP 자산은 런타임 카탈로그와 공용 binding에 등록됐고 심문 HUD는 CP 동전과 HP 하트를 렌더링한다. 다만 진행 기록 화면이 로컬 상수로 계속 `ui/photo/mulkung`을 사용해 coffee 전환은 실제 화면까지 이어지지 않았다.
3. **Submit과 턴 종료가 분리되어 있다.** 유효한 Submit 직후 턴은 그대로이고, 다음 Submit 클릭이 이전 턴 종료와 새 카드 제출을 연달아 수행한다.
4. **현 덱은 비복원추출이다.** 첫 손패 5장 이후 기존 손패를 유지한 채 매 턴 1장만 뽑는다. 손패 전체 폐기와 기본 5종 중복 드로우는 없다.
5. **강압 패배 경계는 감사 도중 병행 변경으로 수정됐다.** 최신 작업 트리는 `coercion >= limit`을 사용하고 일반 100·보스 개별 한계의 equality 실패 테스트도 갖는다.
6. **스위트 스팟 자체는 구현되어 있다.** `balance.sweetSpot = 1~30`을 현재 평정심 최대치의 비율로 환산하고, 필수 목표를 달성한 뒤 명시적으로 진술을 확보하면 BEST가 된다. 다만 결정적 증거 지급과 다음 챕터 강제 연결은 없다.
7. **카드 시각 재료는 대부분 존재하지만 계약은 5개 래스터 레이어다.** 비용·이름·설명이 하나의 copy 컨테이너에 묶여 있어 요청한 8개 독립 레이어 구조와 다르다.
8. **현재 회귀 게이트는 모두 통과하지만 신규 요구 전체가 구현된 것은 아니다.** 강압 경계와 신규 HUD 자산·게이지 단위 테스트는 추가됐지만, 카드가 5개 래스터 레이어라는 구 계약과 다수의 미구현 v2 경로는 그대로다.

Gap Audit은 총 49개 검증 문장으로 세분화했으며, 엄격 판정 결과 **완료 15개 / 미완료 또는 부분 구현 34개**다. 완료 15개에는 8레이어 전체가 아니라 이미 독립 레이어로 동작하는 일부 시각 재료처럼 범위가 좁은 하위 항목도 포함된다.

### 1.4 구현 우선순위

- **P0 — 상태 원자성과 턴 규칙**: 이벤트 HP 0 전역 종료의 원자성, Submit 1회당 정확히 한 턴, 결정론적 5장 드로우
- **P1 — 전투 의미**: 요청 카드 5종, 카드별 수치 단일화, 방어막 2~3개·정답/함정 판정
- **P2 — 화면 전달력**: 브리핑, coffee 최종 바인딩, HP 사용자 문자열, 판정 문구, 8레이어 계약
- **P3 — 로그라이크 확장 및 저장**: 카드 강화, 결정적 증거, 지연 경로 확정·인과율 연계, active encounter save v4/migration
- **P4 — 전체 회귀**: workbench·매뉴얼·자동 플레이·E2E 동기화와 지원 Node 릴리스 게이트

#### 3.1.3 데이터 기반 오프닝 브리핑

사건 ID를 bootstrap에 하드코딩하지 않는다. strict `EncounterSchema`의 최상위에 다음 선택 필드를 추가하고 모든 key는 `LocalizationKeySchema`로 검증한다.

```ts
interface EncounterBriefingDefinition {
  title_key: string;
  body_key: string;
  objective_keys: readonly [string, ...string[]];
  start_label_key: string;
}
```

튜토리얼 물컹이 조우에 이 briefing을 선언하고, 본문 localization 값은 아래 문장을 글자 변경 없이 사용한다.

> 켄타우로스 인사팀장이 야근용으로 아끼던 전설의 '황금 엘릭서 믹스커피'가 사라졌다. 사건 현장인 탕비실 바닥에서 수상한 점액질 자국이 발견됨에 따라, 탕비실 청소를 담당하는 하급 슬라임 '물컹이'가 유력한 용의자로 심문실에 불려 오게 된다. 플레이어는 물컹이를 시작으로 마왕청 내 화이트칼라 마물들을 탐문하며 소소한 사내 범죄의 범인을 추적해야 한다.

정확 본문은 `사건 개요`로, `objective_keys`는 현재 조우에서 검증 가능한 짧은 `목표` 목록으로 별도 렌더링한다. 본문의 마지막 문장만으로 목표를 갈음하지 않는다.

표시 및 상태 계약:

- 첫 `mountInterrogation` 위에 불투명 또는 충분히 어두운 backdrop과 모달을 최상위 z-index로 올린다.
- 모달이 닫힐 때까지 카드·진술·Submit·키보드 단축키와 autoplay action을 모두 막는다.
- 초기 대사/typewriter는 모달의 시작 버튼을 누른 뒤 시작한다.
- RunState/save v4의 `runInstanceId`, `encounterAttemptOrdinal`로 `attemptId = runInstanceId:nodeId:ordinal`을 만들고 bootstrap은 `briefingDismissedAttemptId`만 presentation 상태로 소유한다. 동일 attempt의 Submit remount에는 다시 뜨지 않고 retry 때 ordinal을 올려 다시 표시한다.
- active encounter 저장을 지원한 뒤에는 dismiss 상태도 저장하여 같은 attempt를 새로고침 복원할 때 재표시하지 않는다.
- autoplay port는 브리핑 중 별도 `BRIEFING` scene만 노출하고 `dismissBriefing` 외 submit/endTurn action을 거부한다. 포인터 차단만으로 autoplay를 막았다고 간주하지 않는다.
- 본문 overflow, 1280×800 safe area, 포커스 이동, Escape 정책, 중복 dismiss를 테스트한다.

### 3.2 HUD (CP 동전 / HP 하트 / Gauge Shake)

#### 3.2.1 화면 모델

`InterrogationScreenModel`의 HUD 자원 계약을 다음처럼 명시한다.

```ts
interface InterrogationHudModel {
  turn: number;
  turnLimit: number;
  commandPoints: number;
  commandPointsMax: number;
  hp: number;
  hpMax: number;
  composure: number;
  composureMax: number;
  coercion: number;
  coercionLimit: number;
}
```

- `commandPointsMax`는 `coordinator.resourceLimits.commandPointMax`에서 가져온다.
- `hpMax`는 현 `coordinator.resourceLimits.stressMax`에서 가져와 presentation에서만 이름을 바꾼다. 런별 상한 override가 있으면 이미 계산된 coordinator limit을 우선한다.
- 모든 화면 값은 `[0, max]`로 clamp하되, 엔진 원본 상태가 범위를 벗어나면 개발 모드에서 진단을 남긴다.
- CP는 정수 불변조건을 검증하고 항상 `commandPointsMax`개 슬롯을 그린다. 왼쪽부터 `index < clamp(commandPoints, 0, max)`면 active, 나머지는 deactive다.
- HP는 하트 아이콘 뒤에 `HP current/max`로 표시한다.

#### 3.2.2 legacy stress → HP 표시 호환

v2 요구는 **사용자 명칭과 HUD를 HP로 바꾸는 것**이므로, 저장 호환을 깨뜨리는 전면 필드 rename은 범위에 넣지 않는다.

1. `InterrogationScreenModel`과 사용자-facing presenter에는 `hp`, `hpMax`를 사용하고 엔진의 `resources.stress`, `stressMax`에서 투영한다.
2. Run/Save/Balance/Effect의 `stress`, `APPLY_STRESS`, `STRESS_DEPLETED`는 v2 내부 호환 키로 유지하되 코드 주석에서 legacy technical name임을 명시한다.
3. `resource.stress` localization 값, 회복 보상, dead scene, workbench, 개발 콘솔의 **표시 문자열**을 모두 HP로 바꾼다. JSON ID를 보이게 출력하지 않는다.
4. DP와 신뢰도는 메타 자원으로 유지하되 “4대 심문 상태” HUD에는 포함하지 않는다.
5. 향후 내부 rename이 필요하면 Save version, `CostSchema.stress`, reward `STRESS`, modifier `APPLY_STRESS`, balance `stress.max`, failure reason까지 한 번에 바꾸는 별도 migration으로 처리한다. v2에서 두 이름을 save에 동시에 쓰지 않는다.

HP 0 전역 실패는 이름 변경과 별도로 고친다. 공통 `evaluateRunFailure()`가 현 내부 `stress <= 0`을 판정하며, 조우 진입·유효 Submit 적용 후·이벤트 transaction에 사용된다. 이벤트는 `비용/효과 임시 적용 → HP 검사 → 실패면 nodeIndex·reward를 진행하지 않고 RUN_FAILED 저장 → dead scene` 순서로 처리한다. HP 소진은 Run 실패이므로 retry 없이 새 런만 허용한다.

#### 3.2.3 게이지 컨트롤러와 shake 조건

`gauge.ts`에 이미 도입된 수명주기 계약을 정본으로 사용한다.

```ts
interface GaugeController {
  readonly view: Container;
  readonly shaking: boolean;
  playImpact(): void;
  update(deltaMS: number): void;
  destroy(): void;
}
```

동작 규칙:

- `previousComposure > nextComposure`일 때만 평정심 게이지를 흔든다.
- `previousCoercion < nextCoercion`일 때만 강압 게이지를 흔든다.
- 회복, 동일값, 첫 mount에는 흔들지 않는다.
- 160~220ms 동안 기준 x축에서 최대 ±6px로 감쇠 진동하고 항상 원점으로 복귀한다.
- 연속 입력 시 이전 tween을 취소하고 기준 좌표에서 재시작한다.
- 화면 destroy 시 두 gauge의 `destroy()`를 호출해 진행 중 shake를 release하고 위치를 복원한다.
- 기존 강압 전체 화면 연출은 유지할 수 있으나 게이지 로컬 shake와 책임을 섞지 않는다.

현재 화면은 remount 전후 자원 delta를 비교해 새 gauge의 `playImpact()`를 호출하며, `screenController.update(deltaMS)`가 각 gauge의 `update()`를 호출한다. 아래 3.3의 원자적 Submit을 구현할 때 Coordinator는 `impactFrame`(카드 판정 직후), `settledFrame`(턴 종료·flow 논리 효과까지 정산), `committedFrame`(decision/terminal 또는 다음 턴 시작까지 확정)을 반환한다. `createEncounterSession`은 live coordinator만 읽는 `currentModel()` 외에 순수 `modelForFrame(frame)` projector를 제공해 과거 frame도 UI 모델로 만들 수 있어야 한다. presenter는 세 frame과 출처별 delta를 순서대로 재생하고, committed phase가 `AWAIT_SECURE_DECISION`이면 새 손패 대신 결정 UI를 연다.

### 3.3 턴 Engine & 5카드 무작위 드로우

#### 3.3.1 단일 드로우 정책

앱의 `starting_copies`와 시뮬레이터의 `initial_deck` 이중 소스를 없앤다. 영구 강화와 병합을 수용하기 위해 정의 ID 배열이 아니라 **항상 5개인 draw slot**을 정본으로 둔다.

```ts
interface BasicDrawSlot {
  slotId: string;
  blueprintId: string;
}

interface TurnDrawPolicy {
  handSize: 5;
  slots: readonly [BasicDrawSlot, BasicDrawSlot, BasicDrawSlot, BasicDrawSlot, BasicDrawSlot];
  mode: 'WITH_REPLACEMENT';
  discardRemainingOnValidSubmit: true;
  rngStream: 'CARD_DRAW';
}
```

- 새 런의 5개 slot은 아래 기본 카드 5종의 서로 다른 blueprint를 하나씩 참조한다. `new Set(definitionIds).size === 5`를 검증한다.
- 3단계 병합 후에도 slot 수는 5로 유지한다. 소비된 두 blueprint를 가리키던 두 slot이 같은 합성 result blueprint를 가리켜 합성 카드의 draw 가중치가 2가 된다.
- 초기 손패와 후속 턴 손패가 같은 함수를 사용한다.
- 다른 modifier RNG와 분리된 `CARD_DRAW` stream을 정확히 5번 호출해 각각 `floor(random * 5)`로 slot을 선택한다. stream seed/cursor는 저장한다.
- 선택된 blueprint로 transient `CardInstance`를 만들기 때문에 같은 blueprint가 여러 장 나올 수 있다.
- 영속 deck/blueprint 소유권과 조우 한정 폐기 연출을 분리한다. `turnDiscardHistory`는 직전 전이 presentation에만 보관하고 save에 무한 누적하지 않는다.
- terminal 결과 또는 `AWAIT_SECURE_DECISION`이 된 턴에는 새 손패를 만들지 않는다. 5장 복원추출은 실제 다음 `INPUT` 턴이 시작될 때만 수행한다.
- 저장/재개 후에도 RNG 상태와 손패 instance ID가 같아야 한다.
- 기존 `DRAW_CARD` 효과는 “항상 새 턴 5장”과 충돌하므로 v2 심문 효과에서 제거하거나 다른 비드로우 효과로 마이그레이션하고 semantic validator로 재유입을 막는다.

#### 3.3.2 원자적 Submit과 진술 확보 결정 창 — 확정 규칙

**결론은 “턴 소비”와 “다음 턴 시작”을 분리하는 것이다.** Submit은 카드 턴을 완전히 소비하지만, BEST가 가능한 순간에는 다음 턴을 만들지 않고 명시적 선택 창에 멈춘다. 따라서 “조건 충족 ≠ 자동 종료” 원칙과 “Submit 1회 = 턴 1회”가 동시에 성립한다.

`CHECK_OUTCOME`은 계산 중 잠깐 거치는 transient state로 한정한다. 사용자 입력을 기다리는 stable state로 `AWAIT_SECURE_DECISION`을 새로 추가한다.

| 대안 | 판정 | 이유 |
|---|---|---|
| `secureStatementEnabled`일 때만 `CHECK_OUTCOME`에 체류 | 비채택 | 내부 평가 단계와 사용자 대기 상태가 다시 결합되고, flow 전환·autoplay·save가 같은 상태를 서로 다른 의미로 해석한다. |
| 먼저 다음 턴을 시작해 5장을 뽑고 Secure 버튼 유지 | 비채택 | 쓰지 않을 카드의 RNG를 소비하고 `ON_TURN_START`가 자격을 바꿀 수 있으며 마지막 턴 문제도 별도로 남는다. |
| Submit 정산 후 `AWAIT_SECURE_DECISION` checkpoint | **채택** | 끝난 턴은 원자 commit되고 다음 턴은 아직 존재하지 않아 Secure/Continue, 최종 턴, 저장/재개를 동일 규칙으로 처리한다. |

```text
INPUT
  └─ valid Submit
       → ACTION_RESOLVE / impactFrame / terminal threshold facts 누적
       → 손패 전체 discard / turnsSpent + 1
       → 기존 active modifier의 ON_TURN_END 1회
       → blocking terminal이 없을 때만 목표 갱신 A / flow 논리 효과 1회 commit / 목표 갱신 B
         (threshold fact/authored forced outcome이 있으면 flow를 건너뜀)
       → settledFrame / 필수 실패·강제 자백 판정
             ├─ 발생                         → TERMINAL
             └─ 없음
                  → BEST 자격 판정
                       ├─ 충족               → AWAIT_SECURE_DECISION
                       │    ├─ 진술 확보      → BEST_RESOLUTION
                       │    └─ 심문 계속
                       │         ├─ 잔여 턴 있음 → pending flow 공개 → TURN_START → CP 복원 → 5장 드로우 → INPUT
                       │         └─ 잔여 턴 없음 → PARTIAL_RESOLUTION
                       ├─ 미충족 + 잔여 턴 없음 → PARTIAL_RESOLUTION
                       └─ 미충족 + 잔여 턴 있음 → pending flow 공개 → TURN_START → CP 복원 → 5장 드로우 → INPUT
```

상태 머신 전이:

```text
RUN_MODIFIERS + MODIFIERS_APPLIED              → SETTLE_TURN
SETTLE_TURN + TURN_SETTLED                     → CHECK_FLOW_TRANSITION

CHECK_FLOW_TRANSITION + FLOW_LOGIC_COMMITTED   → CHECK_OBJECTIVES
CHECK_FLOW_TRANSITION + NO_FLOW                 → CHECK_OBJECTIVES
CHECK_OBJECTIVES + OBJECTIVES_CHECKED           → CHECK_OUTCOME

CHECK_OUTCOME + OFFER_SECURE                    → AWAIT_SECURE_DECISION
CHECK_OUTCOME + CONTINUE_NO_FLOW                → TURN_START
CHECK_OUTCOME + CONTINUE_WITH_FLOW              → PRESENT_PENDING_FLOW
CHECK_OUTCOME + COMPLETE_ENCOUNTER              → ENCOUNTER_COMPLETE
CHECK_OUTCOME + FAIL_ENCOUNTER                  → FAILED

AWAIT_SECURE_DECISION + SECURE_STATEMENT       → ENCOUNTER_COMPLETE
AWAIT_SECURE_DECISION + DECLINE_NO_FLOW        → TURN_START
AWAIT_SECURE_DECISION + DECLINE_WITH_FLOW      → PRESENT_PENDING_FLOW
AWAIT_SECURE_DECISION + DECLINE_AND_COMPLETE   → ENCOUNTER_COMPLETE

PRESENT_PENDING_FLOW + FLOW_PRESENTATION_STARTED → RENDER_STATEMENT
RENDER_STATEMENT + STATEMENT_RENDERED            → EMIT_PUBLIC_DTO
EMIT_PUBLIC_DTO + DTO_EMITTED                     → TURN_START

TURN_START + TURN_READY                          → FREE_REVIEW
TURN_START + COMPLETE_ENCOUNTER                  → ENCOUNTER_COMPLETE
TURN_START + FAIL_ENCOUNTER                      → FAILED
```

신규 state는 `SETTLE_TURN`, `AWAIT_SECURE_DECISION`, `PRESENT_PENDING_FLOW`다. 후자는 후속 턴에서 기존 `ENTER_FLOW_NODE`의 **논리 effect 책임만 제거한 presentation 진입점**이며, 기존 `RENDER_STATEMENT → EMIT_PUBLIC_DTO`를 대체하지 않고 앞에 연결한다. 최초 조우의 `ENTER_FLOW_NODE → RENDER_STATEMENT → EMIT_PUBLIC_DTO → TURN_START`는 유지한다. `CHECK_FLOW_TRANSITION` 안에서 pre-flow 목표 갱신 A를 실행한 뒤 pure plan/logical apply를 하고, `CHECK_OBJECTIVES`에서 post-flow 목표 갱신 B를 실행한다.

8단계 매핑은 `PRESENT_PENDING_FLOW`를 `STATEMENT`, `SETTLE_TURN`과 `AWAIT_SECURE_DECISION`을 `END_CHECK`에 포함해 [`TURN_STATE_MAPPING`](../dungeon-dossier/src/engine/encounter/EncounterStateMachine.ts)의 완전성 테스트를 갱신한다. `CHECK_OUTCOME`, `PRESENT_PENDING_FLOW`, `TURN_START`의 진입과 이탈은 한 Coordinator command 안에서 끝나는 transient 단계이며 PublicDTO/autoplay scene으로 직접 노출하지 않는다. 화면은 반환 frame을 나중에 재생하고 그동안 app direction barrier가 입력을 막는다. 결과 phase는 `INPUT ↔ FREE_REVIEW`, `AWAIT_SECURE_DECISION ↔ AWAIT_SECURE_DECISION`, `TERMINAL ↔ ENCOUNTER_COMPLETE | FAILED`로 고정한다.

Coordinator에 한 번의 유효한 플레이를 완결하는 단일 transaction을 둔다. 논리 상태는 한 번에 commit하되 UI가 카드 효과, 턴 정산, 다음 턴 상태를 섞지 않도록 snapshot+knowledge를 묶은 세 frame과 출처별 delta를 반환한다.

```ts
type ResourceDelta = Readonly<Record<EncounterResourceKey, number>>;

interface TerminalThresholdFacts {
  hpDepleted: boolean;
  coercionLimitReached: boolean;
  composureDepleted: boolean;
}

interface EncounterPresentationFrame {
  snapshot: EncounterSnapshot;
  knowledge: EncounterKnowledgeSnapshot;
  presentationRevision: number;
}

interface PendingFlowPresentation {
  targetNodeId: string;
  sourceRevision: number;
  previousPresentationRevision: number;
}

interface PendingSecureDecision {
  decisionId: string;
  sourceRevision: number;
  offeredAfterTurn: number;
  onDecline: 'START_NEXT_TURN' | 'PARTIAL_RESOLUTION';
  contentRevision: string;
  pendingFlowPresentation: PendingFlowPresentation | null;
}

interface SubmitSettlementReceipt {
  impactFrame: EncounterPresentationFrame;    // 효과·modifier·clamp 후, 턴 정산 전
  settledFrame: EncounterPresentationFrame;   // turn-end/flow/목표까지 정산된 끝난 턴
  actionResourceDelta: ResourceDelta;          // preSubmit → impact, CP 비용 포함
  turnEndResourceDelta: ResourceDelta;         // impact → ON_TURN_END 완료
  flowEntryResourceDelta: ResourceDelta;        // flow 진입 전 → settled
  submittedInstanceId: string;
  discardedInstanceIds: readonly string[];
  turnsSpent: number;
}

interface InputCommit {
  phase: 'INPUT';
  committedFrame: EncounterPresentationFrame;
  turnStartResourceDelta: ResourceDelta;        // settled → committed
  drawnInstanceIds: readonly string[];          // P0-4 완료 뒤 length === 5
}

interface TerminalCommit {
  phase: 'TERMINAL';
  committedFrame: EncounterPresentationFrame;
  turnStartResourceDelta: ResourceDelta;
  drawnInstanceIds: readonly [];
  outcome: EncounterOutcome;
}

type ContinuationCommit = InputCommit | TerminalCommit;
type NonBestEncounterOutcome = Exclude<EncounterOutcome, 'BEST_RESOLUTION'>;

type SubmitTransactionResult =
  | {
      kind: 'REJECTED';
      reason: 'CP' | 'TARGET' | 'TAG' | 'EVIDENCE' | 'BUSY';
      snapshot: EncounterSnapshot;
    }
  | ({ kind: 'COMMITTED' } & SubmitSettlementReceipt & ContinuationCommit)
  | ({ kind: 'COMMITTED' } & SubmitSettlementReceipt & {
      phase: 'AWAIT_SECURE_DECISION';
      committedFrame: EncounterPresentationFrame; // settledFrame과 같은 logical revision
      turnStartResourceDelta: ResourceDelta;       // all-zero
      drawnInstanceIds: readonly [];
      pendingDecision: PendingSecureDecision;
    });

type SecureDecisionResult =
  | {
      kind: 'REJECTED';
      reason: 'STALE_DECISION' | 'BUSY';
      snapshot: EncounterSnapshot;
    }
  | ({
      kind: 'COMMITTED';
      decisionId: string;
      choice: 'SECURE';
      settledFrame: EncounterPresentationFrame;
    } & TerminalCommit & { outcome: 'BEST_RESOLUTION' })
  | ({
      kind: 'COMMITTED';
      decisionId: string;
      choice: 'CONTINUE';
      settledFrame: EncounterPresentationFrame;
    } & (
      | InputCommit
      | (TerminalCommit & { outcome: NonBestEncounterOutcome })
    ));
```

`ResourceDelta`는 고정된 모든 자원 key의 `after - before` 값이며 0도 보존한다. `actionResourceDelta`에는 CP 비용과 선택 instance를 source로 한 카드/증거/`ON_RESOLUTION` 효과만, `turnEndResourceDelta`에는 턴 종료 효과만, `flowEntryResourceDelta`에는 node `resource_delta`만, `turnStartResourceDelta`에는 CP 복원·duration tick·턴 시작 효과만 들어간다. 이 경계로 판정 배너, 게이지, 로그가 서로 다른 단계의 수치를 잘못 귀속하지 않는다.

원자 적용 순서:

1. mutation 전에 engine 불변조건 `phase === INPUT`, `currentTurn === turnsSpent + 1`, `turnsSpent < turnLimit`을 assert한다. 위반은 사용자 입력 오류가 아니라 `EncounterInvariantError`로 error boundary에 보내며 preSubmit state를 유지한다. 그 다음 공개 정보로 CP·대상·태그·증거·중복 클릭을 검증한다. 실패는 `REJECTED`이며 어떤 상태도 바꾸지 않는다. Resolver가 `consumeCommandPoints = false`로 돌려주는 `R_ACTION_INVALID`·차단 결과도 같은 REJECTED로 정규화한다. 반면 불충분·무관 증거·진실 공격처럼 **합법적으로 실행된 오답**은 유효한 Submit이므로 CP와 턴을 소비한다.
2. 비용 차감 → 카드/증거 판정 → 카드/조우/유물 modifier → `ON_RESOLUTION` → clamp를 선택 instance를 source로 **정확히 한 번** 적용하고 `impactFrame`과 `actionResourceDelta`를 만든다. 이 단계가 HP 0·강압 한계·평정심 0을 만들면 monotonic `TerminalThresholdFacts`의 해당 bit를 OR하고, resolver의 authored forced outcome은 별도 필드에 보존한다.
3. 선택 instance는 `played/consumed` bookkeeping만 한 번 수행한다. gameplay effect를 다시 적용하지 않는다. 제출 직전 hand의 선택 카드와 나머지 카드를 모두 discard하고 `turnsSpent`를 정확히 1 증가시킨 직후 `turnsSpent <= turnLimit`을 assert한다.
4. Submit 시작 시 캡처한 **flow 진입 전 active modifier 집합**으로 `ON_TURN_END`를 정확히 한 번 수행하고 clamp·`turnEndResourceDelta`·threshold facts를 갱신한다. 이미 true인 bit는 후속 회복으로 false가 되지 않는다. 이후 decision action에서는 이 trigger를 다시 수행하지 않는다.
5. threshold fact가 하나도 없고 authored forced outcome도 없을 때만 목표를 갱신한 뒤 이를 입력으로 순수 `planFlowTransition()`을 호출한다. 선택된 node의 claim revision/reveal, route, modifier 활성·비활성, `resource_delta`, logical current/entered node를 `applyFlowTransition()`으로 한 번 commit하고 clamp·`flowEntryResourceDelta`·threshold facts를 갱신한 뒤 목표를 다시 갱신한다. 새 node modifier는 방금 끝난 턴의 `ON_TURN_END`에 소급 적용되지 않는다. `FlowNode.is_terminal`은 flow tail일 뿐 Encounter outcome으로 자동 변환하지 않는다.
6. `TerminalThresholdFacts`를 `HP 실패 → 강압 실패 → 평정심 0 허위 자백` 우선순위로 reduce한 결과 → authored forced outcome → 최종 상태의 해결 불가 순으로 필수 결과를 평가한다. 예를 들어 action에서 평정심 0, `ON_TURN_END`에서 HP 0이면 두 bit가 남고 HP 실패가 이긴다. 하나라도 발생하면 진술 확보 창 없이 `TERMINAL`을 commit한다. `NO_SOLVABLE_PATH`는 flow가 실행된 경우 새 claim/route가 열린 뒤, flow를 건너뛴 경우 현재 정산 상태에서 평가한다.
7. `turnsSpent` 증가 직후부터 유지한 `turnsSpent <= turnLimit` assert를 outcome 분기 전에 다시 확인한다. 초과 상태를 BEST/PARTIAL로 숨기지 않고 손상된 state/save로 거부한다.
8. 필수 결과가 없고 BEST 자격을 만족하면 손패가 빈 상태로 `AWAIT_SECURE_DECISION`을 canonical snapshot에 commit한다. CP 복원, `ON_TURN_START_PRE_DRAW`, RNG 소비, 5장 드로우, 새 round의 PublicDTO 공개는 아직 하지 않는다. flow 논리 효과는 이미 확정됐으며 decision 때문에 rollback하지 않는다.
9. BEST 자격이 없고 `turnsSpent === turnLimit`이면 PARTIAL을 commit한다. `turnsSpent < turnLimit`일 때만 아래 공용 `startNextTurn()`을 실행한다.

`startNextTurn()` 계약:

1. `pendingFlowPresentation`이 있으면 논리 효과를 재실행하지 않고 새 statement/knowledge PublicDTO만 공개하며 `PRESENT_PENDING_FLOW → RENDER_STATEMENT → EMIT_PUBLIC_DTO → TURN_START`로 이동한다. 없으면 바로 `TURN_START`다.
2. `currentTurn = turnsSpent + 1`로 증가시키고 CP 복원·duration tick·hand 비의존 `ON_TURN_START_PRE_DRAW`를 commit한다. 여기서 terminal threshold fact가 생기면 문서 우선순위로 reduce하고, 증가한 `currentTurn`과 자원 정산은 유지하되 hand/RNG 변화 없이 `TERMINAL`을 반환한다.
3. 안전하면 전용 `CARD_DRAW` stream으로 손패를 만든 뒤 `ON_HAND_READY`의 instance lock/표시만 적용하고 `INPUT`을 commit한다. 초기 조우도 `turnsSpent = 0`, `currentTurn = 1`로 같은 pre-draw/draw/hand-ready 경로를 사용한다.
4. v2 심문의 `ON_TURN_START_PRE_DRAW`/`ON_TURN_END`에는 `DRAW_CARD`, `DISCARD_CARD`, hand selector를 금지한다. `LOCK_CARD`는 `ON_HAND_READY`의 blueprint→instance 투영으로 마이그레이션하고, `ON_HAND_READY`는 자원 변경이나 추가 draw/discard를 허용하지 않는다.

결정 action 계약:

- `resolveSecureDecision(decisionId, 'SECURE')`는 flow 논리 효과를 보존하되 미공개 presentation을 폐기하고 추가 턴·modifier·draw 없이 BEST를 확정한다.
- `resolveSecureDecision(decisionId, 'CONTINUE')`는 턴을 추가 소비하지 않는다. `onDecline`이 `START_NEXT_TURN`이면 저장된 presentation을 공개한 뒤 `startNextTurn()`을 한 번 호출하고, `PARTIAL_RESOLUTION`이면 손패/RNG 변화 없이 미공개 presentation을 폐기하고 부분 해결로 종료한다.
- 마지막 허용 턴에 스위트 스팟을 만든 경우에도 PARTIAL보다 결정 창이 우선한다. `진술 확보`는 BEST, `심문 계속`은 “확보 포기 · 부분 해결”로 명확히 표시한다.
- decision 중에는 게임 상태가 동결된다. 타이머, modifier, 추가 logical flow transition, pending presentation publish, card input은 실행하지 않는다.
- `decisionId`는 `encounterAttemptId:turnsSpent:sourceRevision`에서 결정론적으로 만들고 canonical snapshot에 둔다. `sourceRevision`은 accepted engine command에서만 1 증가하며 render/save 횟수와 무관하다. ID/revision이 다르거나 이미 소비된 요청은 `STALE_DECISION`으로 거부해 더블 클릭·remount·autoplay 중복 호출을 멱등 처리한다.

불변 조건:

- valid Submit은 성공/오답/decision/terminal 여부와 무관하게 `turnsSpent +1`; decision 선택은 `+0`이다.
- `currentTurn`은 실제 `TURN_START`가 시작될 때 증가한다. Submit 직후 decision/terminal에서는 방금 끝난 턴 번호를 유지하지만 `ON_TURN_START_PRE_DRAW` terminal은 새 턴 번호와 CP/duration 정산을 유지한다.
- `CHECK_OUTCOME`에서는 외부 입력을 받지 않으며 transaction이 그 상태로 반환되어서는 안 된다.
- 같은 정의 카드가 세 장이면 선택한 instance 한 장만 효과/played 판정을 받고, 이후 나머지 두 장을 포함한 손패 전체가 discard된다.
- `bootstrap.ts`의 “다음 Submit에서 이전 `endTurn()` 호출” 분기와 public `endTurn()` action을 제거한다. turn 정산은 Submit 내부 전용 함수 하나만 소유한다.
- 현 `#runFlow()`의 “전환 계산+즉시 mutation+화면 공개”를 순수 plan, logical apply, presentation publish로 분리한다. Submit은 logical apply를 한 번 commit하고 `pendingFlowPresentation`만 남긴다. Secure는 논리 효과가 아니라 presentation만 폐기하며 Continue는 효과를 재적용하지 않는다.
- logical `flowNodeId/revealedIds`와 공개 cursor를 분리한다. AWAIT의 snapshot은 새 논리 상태를 가지지만 `knowledge`/PublicDTO는 이전 `presentationRevision`으로 투영해 다음 진술·숨겨진 claim을 rail 뒤로 누출하지 않는다. Continue에서만 cursor를 전진시킨다.
- Submit settlement 또는 final-turn decision에서 `TERMINAL`을 확정하는 공용 `finalizeSettlementTerminal()`은 flow logical effect를 보존하되 `pendingFlowPresentation = null`, presentation cursor 미전진, hand 0, draw/RNG 변화 0으로 만든다. 이는 flow-entry hard terminal, `NO_SOLVABLE_PATH`, non-BEST PARTIAL, Secure, 마지막 턴 Continue 모두에 적용한다. 이미 Continue가 presentation을 승인한 뒤 `ON_TURN_START_PRE_DRAW`에서 terminal이 된 경우만 cursor가 전진한 상태를 유지하며, pending은 null이고 draw/RNG는 여전히 0이다.
- presenter는 입력을 잠그고 `impactFrame → settledFrame → committedFrame` 순서로 판정 배너·게이지·discard·결정/결과/새 손패를 재생한다. 동일 revision frame을 remount해도 효과를 재실행하지 않는다.
- transaction 도중 resolver, modifier, objective, flow 어느 단계에서 예외가 나면 CP·hand/discard·turn·machine·revision·RNG를 포함한 preSubmit state로 전부 rollback한다.
- P0-3은 `turnsSpent`, 빈 hand, RNG cursor, pending decision/flow presentation을 포함한 committed snapshot codec과 같은 프로세스의 remount까지만 보장한다. 실제 브라우저 재실행 후 active encounter disk 복원은 P3 save v4 수용 범위이며, 그때 `impactFrame`이 아니라 committed canonical state만 저장한다.

#### 3.3.3 중복 카드 인스턴스

정의, 영구 강화 blueprint, 일회성 손패 instance를 분리한다. attachment의 정본은 blueprint 하나에만 둔다.

```ts
interface CardInstance {
  instanceId: string;
  blueprintId: string;
}

interface RunIdentityState {
  runInstanceId: string;
  encounterAttemptOrdinal: number;
  nextDrawSerial: number;
}
```

- 선택, drag, hover, Map 키, evidence docking, 강화 대상은 `instanceId`를 사용한다.
- 효과와 표시는 `instance → blueprint → definition/attachments` 순서로 해석한다.
- 새 런 생성 시 `runInstanceId`를 한 번 만들고 저장한다. encounter 진입·retry 때만 `encounterAttemptOrdinal`을 증가시키며 Submit remount에는 증가시키지 않는다.
- instance ID는 `nodeId:attemptId:nextDrawSerial`로 만들고 serial을 draw마다 증가·저장해 retry/재진입에서도 충돌하지 않게 한다.
- 구 save에는 migration 시 `runInstanceId`를 한 번 생성하고 ordinal/serial을 현재 encounter 상태에서 복원하거나 0으로 초기화한 뒤 즉시 v4로 다시 저장한다.
- evidence docking과 선택 highlight는 instance ID 단위로 동작한다.

#### 3.3.4 기본 카드 5종 정본

기존 14장 고정 길이 schema를 제거하고 신규 ID를 정본으로 삼는다. 구 카드/보상/강화 참조는 migration 표로 교체하거나 legacy 콘텐츠로 명시하며, production 기본 draw slot에는 아래 5종만 들어간다.

| 카드 / ID | 역할 | CP | 대상·증거 | 방어막 처리 | 방어막 피해 | 기본 평정심 | 기본 강압 | 일러스트 |
|---|---|---:|---|---|---:|---:|---:|---|
| 유도 신문 / `card_leading_question` | 기본 잽 | 1 | GAP은 무증거, SHIELDED 시 증거 정확히 1개 | `BREAK_ON_DIRECT` | 1 | -10 | +2%p | `00` |
| 서류철 툭 던지기 / `card_toss_dossier` | 멘탈 조절 | 1 | GAP 또는 BROKEN, 증거 없음 | `BLOCKED` | 0 | -10 | 0 | `01` |
| 모순 지적 / `card_point_contradiction` | 주력기 | 2 | BROKEN, 증거 정확히 1개 | `REQUIRE_BROKEN` | 0 | -25 | +5%p | `02` |
| 결정적 물증 / `card_decisive_proof` | 주력기 | 2 | 모든 진술, 증거 정확히 1개 | `IGNORE` | 0 | -20 | 0 | `03` |
| 알루미늄 배트 위협 / `card_bat_threat` | 물리/강압 | 2 | 모든 진술, 증거 없음 | `IGNORE` | 0 | -30 | +15%p | `04` |

`ui_card_illust05`는 3단계 합성 카드용으로 예약한다. 배트에는 `HOT_TEMPER_RISK` 경고 태그를 두어 다혈질 용의자의 추가 반발 modifier 가능성을 설명하되, 기본 +15%p와 혼합해 하드코딩하지 않는다.

권장 도메인 계약:

```ts
interface CardCombatProfile {
  role: 'BASIC_JAB' | 'MENTAL_CONTROL' | 'FINISHER' | 'PHYSICAL_COERCION';
  composureDelta: number;
  coercionDelta: number;
  targetRule: 'GAP_OR_SHIELD_ATTEMPT' | 'GAP_OR_BROKEN' | 'BROKEN' | 'ANY_CLAIM';
  evidenceMode: 'NONE' | 'OPTIONAL_FOR_SHIELD' | 'EXACTLY_ONE';
  shieldMode: 'BREAK_ON_DIRECT' | 'BLOCKED' | 'REQUIRE_BROKEN' | 'IGNORE';
  shieldDamage: 0 | 1;
}
```

진술 노출 상태는 `GAP | SHIELDED | BROKEN` 세 가지로 단순화한다. 방어막이 없는 진술은 GAP, 방어막이 깨지면 BROKEN이다. SHIELDED 진술에 유도 신문+증거를 제출하는 것은 정답 여부를 사전 노출하지 않는 **유효한 시도**이며, Resolver가 증거 관계를 판정한다.

단일 판정 순서:

1. 공개 정보만으로 대상 상태, CP, 증거 개수 등 구조적 validation을 수행한다. 실패하면 `REJECTED`다.
2. 카드 profile에 유물/강화/조우 modifier를 적용해 raw 평정심·강압 수치를 만들되 아직 자원에는 쓰지 않는다.
3. 증거형 공격은 relevance/relation/sufficiency/independence로 기존 resolution code를 계산한다.
4. `R_DIRECT_CONTRADICTION`: raw 평정심 피해를 전부 적용한다. `BREAK_ON_DIRECT`는 내구 1을 0으로 만들고 같은 hit에서 피해를 주며, `IGNORE`는 내구를 유지한다.
5. `R_INDIRECT_SUSPICION`: shieldDamage는 0이다. GAP/BROKEN 대상에만 raw 평정심 피해의 50%를 0 방향 반올림해 적용하고, SHIELDED에는 평정심 피해 0이다. 카드 고유 강압은 적용한다.
6. `R_INSUFFICIENT_GROUNDS`: 모든 outgoing 평정심/shield 피해를 최종 단계에서 0으로 막고 `카드 고유 강압 + insufficientPenalty(기본 2%p)`를 적용한다.
7. `R_IRRELEVANT_EVIDENCE`: 모든 outgoing 평정심/shield 피해를 최종 단계에서 0으로 막고 `카드 고유 강압 + irrelevantPenalty(기본 5%p)`를 적용한다.
8. `R_TRUTH_ATTACKED`: `IGNORE` 및 모든 유물/강화 damage modifier보다 우선하는 최종 damage gate로 평정심/shield 피해를 0으로 막고 `카드 고유 강압 + truthAttackPenalty(기본 15%p)`를 적용한다.
9. 비증거 배트도 SHIELDED 대상의 domain truth를 Resolver가 검사한다. 진짜 거짓말이면 방어막을 무시해 -30/+15%p, 진실 함정이면 피해 0/+30%p다. UI에는 truth를 사전 노출하지 않는다.
10. 모든 `+N%`는 조우 limit의 비율이 아니라 0~100 강압 축의 **절대 percentage point**다. 보스 limit 40에서도 +15는 +15점이다.
11. 카드 profile이 명목 위력의 단일 정본이며 기존 `balance.resolution` 피해를 더하지 않는다. resolution gate를 통과한 최종 delta만 자원에 적용한다.

따라서 대표 결과는 다음과 같다.

| 상황 | 결과 |
|---|---|
| 유도 신문 + 거짓 SHIELDED + 모순 증거 | 방어막 1→0, 평정심 -10, 강압 +2 |
| 유도 신문 + 진실 SHIELDED + 지지 증거 | 방어막/평정심 변화 0, 강압 +17 |
| 유도 신문 + 부분 모순 증거 | 방어막 변화 0; GAP/BROKEN이면 평정심 -5, 강압 +2 |
| 증거형 카드 + 불충분/무관 증거 | 평정심/방어막 0, 카드 고유 강압 +2/+5 |
| 결정적 물증 + 거짓 SHIELDED + 모순 증거 | 방어막 유지, 평정심 -20, 강압 0 |
| 결정적 물증 + 진실 진술 + 지지 증거 | 평정심 0, 강압 +15 |
| 배트 + 거짓 SHIELDED 또는 비방어 진술 | 방어막 유지, 평정심 -30, 강압 +15; trait modifier는 별도 |
| 배트 + 진실 SHIELDED | 방어막/평정심 변화 0, 강압 +30 |

카드명, 역할, 증거 요구, 실제 수치, 강압 단위, 방어막 상태를 localization 설명에 그대로 노출한다.

#### 3.4.1 고정 레이어 계약

`CARD_LAYER_IDS`와 z-index를 다음 순서로 고정한다.

| z | 레이어 ID | 책임 | 입력/자산 |
|---:|---|---|---|
| 0 | `base` | 카드 베이스·하단 레이아웃 | `ui_card_base.png`; ref는 제작 참고만 |
| 1 | `cost` | CP 숫자와 active 동전 | CP icon + 비용 텍스트 |
| 2 | `name` | 카드 이름 | localized name |
| 3 | `ability` | 분류·조건·효과 설명 | localized rules + 실제 수치 |
| 4 | `illust` | 카드 일러스트 | `ui_card_illust00`~`05` |
| 5 | `stamp` | 평정심/강압 결재 도장 | `ui_card_stamp_logic/pushy` |
| 6 | `post` | 형광 포스트잇 타격 모듈 | `ui_card_post` |
| 7 | `evidence` | 서류 클립/폴라로이드 | `ui_card_evidence00`~`05` |

구현 규칙:

- 모든 레이어는 항상 존재하는 named Container이며, 선택 자산이 없을 때만 내부가 빈다.
- 비용·이름·능력을 현재의 단일 copy container에서 분리한다.
- 레이아웃 계산과 drawing 함수를 분리해 텍스트만 바뀌어도 다른 레이어를 재생성하지 않는다.
- 레이어 순서 테스트는 정확히 8개 ID와 오름차순 z-index를 검증한다.
- 증거물을 탈착해도 stamp/post 상태가 사라지지 않아야 한다.
- 카드 강화의 여러 효과를 한 레이어에 표시할 때는 레이어 자체를 추가하지 말고 해당 레이어 내부에서 정해진 슬롯에 합성한다.
- 요청 순서를 지키면서도 illustration/attachment가 텍스트를 덮지 않도록 cost/name/ability rectangle과 stamp/post/evidence rectangle의 비중첩을 layout test로 고정한다.
- lock/debuff/focus/selection은 8개 콘텐츠 레이어에 포함하지 않는 보조 overlay다. `lock = 8`, `debuff = 9`, `focus/selection = 10` 이상으로 재지정해 evidence 아래에 깔리지 않게 한다.

#### 3.4.2 판정 피드백 계약

배너는 모호한 서사 문구보다 판정 종류와 실제 delta를 먼저 보여준다.

| 판정 | 헤드라인 예시 | 필수 수치 표기 | 톤 |
|---|---|---|---|
| 직접 모순 | `모순 입증 성공` | 실제 `평정심 Δ · 강압 Δ` | 성공 타격 |
| 진실 공격 | `오답 공격` | 실제 `평정심 0 · 강압 +N%p` | 명확한 페널티 |
| 진술 지지 | `진술 일치 확인 · 공격 아님` | 발생한 delta만 | 중립/확인 |
| 사용 불가 | `카드를 사용할 수 없음` | 사유: CP/태그/대상 | 무효, 턴 미소모 |

- 문구의 숫자는 raw resolution이 아니라 카드·조우·유물·강화 modifier와 clamp를 모두 적용한 뒤의 `SubmitTransactionResult.actionResourceDelta`에서 만든다. 턴 종료·flow entry·다음 턴 시작 delta는 별도 상태 로그로 표시하고 카드 타격 수치에 합산하지 않는다.
- 명목 위력과 실제 변화가 다르면 `평정심 -10 (위력 25)`처럼 분리한다. HP/평정심 하한 때문에 실제 -10인데 -25로 표시하지 않는다.
- `진술이 증거와 맞물렸다`는 공격 성공처럼 읽히지 않도록 위의 중립 문구로 교체한다.
- 색상만으로 성공/오답을 구분하지 않고 텍스트·아이콘·수치를 함께 사용한다.
- 628px 배너의 첫 줄은 항상 `판정 헤드라인 + delta`, 둘째 줄에 진술/증거 요약을 두어 긴 인용문이 핵심 판정을 ellipsis로 밀어내지 못하게 한다.
- CP/태그/대상 오류는 throw가 아니라 비변경 `REJECTED` 결과를 받아 같은 형식의 사용 불가 배너를 표시한다.
- 애니메이션 전에 판정 결과를 확정하고, 중복 클릭으로 배너와 상태가 두 번 적용되지 않게 한다.

### 3.5 대질 심문 & 스위트 스팟 / 인과율 시스템

#### 3.5.1 자원과 종료 규칙

| 자원 | 시작/상한 | 감소·증가 의미 | 종료 조건 |
|---|---|---|---|
| HP | 런 시작 시 최대 | 이벤트 비용, 장기 수사 피해 | `HP <= 0` 즉시 Run 실패 |
| 강압 수사 | 0에서 시작, 일반 100 | 오답·강압 카드로 증가 | `coercion >= limit` 즉시 실패 |
| 평정심 | 용의자별 최대치 | 정확한 논박·압박으로 감소 | 0이면 허위 자백; 1~30%는 스위트 스팟 후보 |
| CP | 조우 설정 상한 | 카드 사용 비용 | 턴 시작 시 설정값으로 복원 |

각 자원 변경 phase마다 HP 소진·강압 한계·평정심 0을 monotonic `TerminalThresholdFacts` bitset에 OR한다. action 또는 `ON_TURN_END`에서 bit가 생기면 flow 진입은 생략하고, flow node entry가 임계치를 만들면 그 직후 bit를 추가한다. 후속 회복은 이미 true인 bit를 지우지 않는다. 최종 Submit 우선순위는 `HP bit → 강압 bit → 평정심 0 bit → authored 강제 결과 → 해결 불가 실패 → 스위트 스팟 decision → turnsSpent === turnLimit PARTIAL → 다음 턴`이다. 마지막 허용 턴의 스위트 스팟 기회를 보존하기 위해 PARTIAL은 decision보다 뒤다. Submit 진입 전 `turnsSpent < turnLimit`, 증가 직후 `turnsSpent <= turnLimit`을 assert하며 초과는 정상 gameplay 결과가 아니라 save/엔진 불변조건 위반으로 진단한다.

#### 3.5.2 활성 라운드, 6개 진술, 다중 방어막

원문의 “턴 시작 시 6개 태그”는 **매 턴 active round의 6개 태그를 보드에 배치한다**는 뜻으로 적용한다. `round`는 여러 카드 턴 동안 유지되는 서사 phase이며 `turn`과 분리한다. 그래야 한 턴에 유도 신문으로 깬 방어막을 다음 턴의 모순 지적으로 공격할 수 있다.

```ts
interface InterrogationRoundState {
  activeRoundIndex: number;       // logical flow가 확정한 판정 정본
  presentedRoundIndex: number;    // PublicDTO가 마지막으로 공개한 round
  claimIdByFacet: Readonly<Record<'WHO' | 'WHEN' | 'WHERE' | 'WHAT' | 'HOW' | 'WHY', string>>;
  shieldDurabilityByClaimId: Readonly<Record<string, number>>;
}
```

콘텐츠 정적 검증 규칙:

1. `rounds.length`와 `estimated_turns`는 독립이다. `currentTurn`이 증가해도 round transition 조건이 충족되지 않으면 `activeRoundIndex`는 유지된다. Submit settlement에서 logical round가 먼저 확정된 경우 `presentedRoundIndex`는 Continue의 `PRESENT_PENDING_FLOW`까지 이전 값을 유지하며, `INPUT`에서는 두 값이 반드시 같다.
2. 각 round는 WHO/WHEN/WHERE/WHAT/HOW/WHY 슬롯에 정확히 하나씩, 총 6개 진술을 갖는다. v2에서는 compound/multi-claim facet을 금지하고 각 key가 가리키는 claim의 실제 facet도 일치해야 한다.
3. 각 round의 방어막은 2개 또는 3개이고 v2 durability는 모두 1이다.
4. shield의 claim ID는 같은 round에 속해야 한다.
5. 방어막 중 정확히 하나만 **그 round에서 획득/사용 가능한 증거와 proof rule로 `R_DIRECT_CONTRADICTION`에 도달 가능한 약점**이어야 한다. 단순 truth enum만 세지 않는다.
6. 나머지 방어막은 각자 supporting evidence로 `R_TRUTH_ATTACKED`에 도달 가능한 진실 함정이어야 한다.
7. 공개 데이터는 facet·문장·내구·파괴 여부뿐이며 proof truth와 정답 shield ID는 UI에 노출하지 않는다.

판정 규칙:

- 유도 신문 + 거짓 방어막 + 충분한 모순 증거: 내구 1→0, `BROKEN`, 같은 hit에서 -10/+2%p.
- 유도 신문 + 진실 방어막 + 지지 증거: 방어막·평정심 변화 0, +17%p(카드 2 + 오답 15).
- `REQUIRE_BROKEN`은 공개 상태가 BROKEN이 아니면 validation 실패다.
- 증거형 `IGNORE` 카드도 evidence relation을 먼저 판정하므로 진실 공격에는 피해가 없다. 배트도 진실 방어막이라는 domain truth를 우회하지 못하며 오답이면 피해 0/강압 페널티가 적용된다.
- 방어막 파괴만으로 round를 넘기지 않는다. BROKEN 약점에 모순 지적이 성공해 claim이 `REFUTED`되고 authored `advance_when` 목표가 충족되거나 명시적 flow node가 실행될 때만 다음 round로 이동한다.
- 다음 턴에는 같은 active round의 6진술과 방어막 상태를 다시 투영한다. 실제 round transition 때만 새 6진술·2~3방패로 교체하고 이전 상태를 활성 판정에서 격리한다.

현재처럼 모든 round claim을 시작 시 flatten하지 않고 active round만 UI와 Resolver에 제공한다. 기존 콘텐츠는 각 round마다 6진술·2~3방패·proof solvability·명시적 `advance_when`을 갖도록 증설한다.

P3 저장은 기존 `SavedEncounterStateSchema.round_index`를 logical `activeRoundIndex`에 배선하고, 공개 cursor는 `presentationRevision/presentedRoundIndex`로 분리한다. 현재 [`runSave.ts`](../dungeon-dossier/src/app/save/runSave.ts)가 `encounter: null`로 쓰는 경로를 고쳐 active hand instance, `currentTurn`, `turnsSpent`, 두 round cursor, shield durability, `CARD_DRAW` cursor까지 committed state로 저장·복원한다.

#### 3.5.3 스위트 스팟과 결정적 증거

기존 1~30% 계산과 명시적 `진술 확보` 선택은 유지하되, 자격 판정과 확정 action을 분리한다. Submit transaction이 `ON_TURN_END`와 node entry의 논리 효과·목표 재평가까지 정산한 `settledFrame`에서 아래 자격을 평가한다.

```text
bestEligible = 필수 목표 완료
AND 0 < composure / composureMax <= 0.30
AND coercion < encounterLimit
AND (authored state_conditions.coercion_max 없음 OR coercion <= coercion_max)

BEST_RESOLUTION = bestEligible
AND pending secure decision에서 playerChoice == SECURE
```

- 자격 충족은 자동 종료가 아니라 `AWAIT_SECURE_DECISION` 진입만 만든다. `secureStatementRequested` boolean을 일반 OutcomeEvaluator에 섞지 않고, 저장된 pending decision을 소비하는 별도 command로 BEST를 확정한다.
- HP 0, 강압 한계 도달, 해결 경로 소멸, 평정심 0은 자격보다 먼저 판정한다. 동일 Submit에서 함께 발생하면 decision을 열지 않는다.
- 마지막 허용 턴에서도 `bestEligible`이면 먼저 decision을 연다. Secure는 BEST, Continue는 PARTIAL이다. 이 규칙으로 마지막 카드가 만든 스위트 스팟을 실제로 확보할 수 있다.
- `ON_TURN_END`는 Secure/Continue 선택과 무관하게 Submit transaction에서 한 번 적용한다. 승리 선택으로 턴 종료 페널티를 건너뛰는 분기를 만들지 않는다. “심문을 계속할 때만” 필요한 효과는 별도 `ON_INTERROGATION_CONTINUE` trigger로 모델링한다.
- node entry의 resource/claim/objective 효과로 새로 자격을 얻을 수 있으며 Secure를 골라도 이 논리 효과를 rollback하지 않는다. 다만 새 statement와 미공개 claim은 `presentationRevision`으로 가려 Continue 전 PublicDTO에 노출하지 않는다.
- P0-3 앱 연결은 빈 손패 위치의 Pixi inline decision rail과 키보드 좌/우·Enter/Space owner를 제공하고, 카드·태그·Submit·파트너·조서 입력을 모두 잠근다. 이 단계에는 dismiss/Escape 동작이 없고 Escape는 no-op이다.
- P2 최종 UI에서는 **각각의 새 pending decision 최초 표시**를 판정·게이지 연출이 끝난 뒤 차단형 DOM dialog로 알린다. 문구는 `결정적 진술을 확보할 수 있습니다`, 현재 평정심/허용 범위, 확보 시 종료 효과를 포함한다. 같은 `decisionId`의 remount/복원에서 `acknowledgedDecisionId`가 일치할 때만 dialog 대신 DOM inline rail을 복원하며, 새 decision은 새 dialog다.
- dialog에는 `진술 확보하고 종료`와 `심문 계속` 두 gameplay action을 둔다. 마지막 턴의 secondary는 `확보 포기 · 부분 해결`로 바꾼다. 첫 focus는 action이 아닌 `tabindex=-1` 제목 또는 `결정 창 축소`에 둔다.
- Escape와 X는 engine command가 아닌 `DIALOG_OPEN → INLINE_RAIL` presentation 전이만 만든다. native dialog의 `cancel`을 `preventDefault()`하고 acknowledgment를 기록한 뒤 의도적으로 닫으며, backdrop은 무동작이다. 어느 경로도 Secure/Continue로 매핑하지 않는다. 닫힌 뒤 focus는 rail 제목으로 옮기고 `결정을 내려야 심문이 진행됩니다`를 알린다.
- dialog에는 `aria-modal`과 focus trap, rail에는 labelled `role=group`, 공통으로 44px 이상 버튼, visible focus, `aria-live=polite`, reduced-motion을 적용한다. callback은 `decisionId`를 재검증하며 dialog/rail 어느 쪽에서도 base Pixi input lock을 풀지 않는다.
- autoplay에는 presenter의 impact/settlement direction barrier가 끝나 UI와 같은 tick에 `SECURE_STATEMENT_DECISION { decisionId, secure(), continue() }`만 노출한다. 그 전에는 `BUSY/DIRECTION`이며 Submit/endTurn/dismiss는 노출하지 않는다. 정책은 아래와 같이 고정하고 fuzz 결정에는 `CARD_DRAW`와 분리된 seeded stream을 쓴다.

| autoplay policy | decision | 목적 |
|---|---|---|
| `best` | Secure | BEST 경로 확정 |
| `greedy` | Secure | 이용 가능한 상위 결과 즉시 획득 |
| `partial` | Continue | PARTIAL 경계 탐색 |
| `coerced` | Continue | 강압/허위 자백 경로 탐색 |
| `fuzz` | 별도 RNG로 25% Secure, 75% Continue | 두 branch의 결정론적 탐색 |

- P0-3 snapshot codec은 canonical `PendingSecureDecision`과 같은 프로세스의 `acknowledgedDecisionId` remount를 지원한다. 실제 mid-encounter disk save는 P3 v4에서 committed state, `pendingFlowPresentation`, content revision, acknowledgment를 함께 저장한다. `modalOpen` 같은 일시 DOM 상태나 `impactFrame`은 저장하지 않으며, 복원 시 gameplay state를 재평가하거나 효과를 replay하지 않는다. content revision이 맞지 않으면 pending decision을 현재 balance로 재계산하지 말고 호환 불가 recovery로 보낸다. 저장 write 실패는 accepted command를 되감거나 재Submit하지 않고 동일 revision payload의 재시도만 허용하며, 성공 전에는 node navigation을 막는다.
- 일반 조우의 BEST는 보상/진행만 확정한다. **보스 조우에서 확정된 BEST**에만 아래 결정적 증거를 지급한다.
- 평정심 0의 허위 자백, PARTIAL, FAILED에는 지급하지 않는다.
- 결정적 증거의 정본 타입은 별도 임시 token이 아니라 **Relic**으로 고정하며 ID는 `relic_decisive_evidence_<caseId>`다.
- boss 여부는 EncounterCoordinator가 아니라 현재 node kind를 아는 Run 계층이 판정한다. BOSS outcome 콘텐츠의 `unlock_causal`은 아래 `causal_link_id`를 참조하고, 해당 link가 지정한 Relic을 함께 지급한다.
- 보상 적용은 idempotent해야 하며 같은 보스 재평가/재개로 중복 지급하지 않는다.
- UI는 “결정적 증거 획득”과 연계될 다음 사건의 힌트를 보여주되, 아직 해금되지 않은 사건의 정답은 노출하지 않는다.

#### 3.5.4 3단계 카드 강화

기존의 “보유 시 모든 호환 카드에 자동 발동” 모델과 별도 `cardTuning` 모델을 blueprint 중심으로 통합한다. 탈착 모듈은 수량과 개체성을 보존한다.

```ts
interface EnhancementModuleInstance {
  moduleInstanceId: string;
  definitionId: string;
  type: 'STAMP' | 'POST_IT' | 'CLIP';
}

interface EnhancementInventory {
  unassignedModuleIds: readonly string[];
  modulesById: Readonly<Record<string, EnhancementModuleInstance>>;
}

interface PersistentCardBlueprint {
  blueprintId: string;
  definitionId: string;
  stampModuleIds: readonly string[];
  postitModuleIds: readonly string[];
  tuning: CardTuning;
}
```

- **1단계 — 결재 도장**: 선택한 blueprint에 module instance 하나를 영구 부착하고 inventory에서 소비한다. 일반 blueprint는 stamp 1슬롯이며 파란 도장은 논리/안정, 붉은 도장은 강압/위험 효과를 데이터로 선언한다.
- **2단계 — 형광 포스트잇**: “1회차”를 **첫 전체 Run 클리어**로 해석해 profile/meta-progression의 `unlock_postit_attachment`를 영구 해금한다. run save와 분리한다. 일반 blueprint는 post-it 1슬롯이며 장착/탈착 시 inventory와 원자 교환하고, 제출 target facet과 일치할 때만 발동한다.
- **3단계 — 서류 클립**: clip module과 recipe가 지정한 두 blueprint를 한 transaction에서 소비하고 result blueprint를 만든다. 두 source를 가리키던 draw slot은 모두 result를 가리킨다.
- 합성 result는 source의 **module instance 배열을 중복 제거 없이** 안정 순서로 모두 상속한다. 같은 색 도장 두 개도 서로 다른 instance이므로 두 효과를 보존한다. 일반 슬롯 상한은 합성 result의 inherited slot에는 적용하지 않으며 UI stamp/post 레이어 내부에서 최대 2개씩 배치한다.
- 합성 뒤 result definition과 상속 module의 원래 호환성이 달라도 “그대로 상속” 요구에 따라 inherited 효과를 유지한다. 새로 장착할 때만 result 호환성을 검사한다.
- tuning은 각 필드마다 `clamp(recipe.result_base_tuning + left.tuning + right.tuning, authoredTuningBounds)`으로 병합한다. 그 뒤 최종 CP는 0 이상, 평정심/강압 효과는 schema 상한 안인지 다시 검증한다. 어느 재료가 왼쪽인지에 따라 결과가 달라지면 안 된다.
- 정적 `card_modifier`는 시작 카드의 초기 attachment로 마이그레이션한다.
- 기존 Pattern-D `cardTuning`은 blueprint의 실제 비용·평정심·강압 계산에 연결하고 definition ID별 구 tuning은 해당 초기 blueprint에 복사한다.
- 기존 `acquiredEnhancementIds`는 어느 카드에 붙었는지 알 수 없으므로 save migration 시 수량 1의 **미장착 inventory module**로 변환해 사용자가 배정하게 한다.
- 현 `enh_clip_commit`은 병합 recipe가 아닌 전역 COMMITTED 효과다. 진행 중 구 런에서는 `legacyPassiveEnhancementIds`로 런 종료까지 의미를 보존하고, 새 런부터는 동명의 신규 병합 clip을 지급하지 않는다. 별도 신규 clip/recipe ID를 사용한다.
- 저장에는 draw slot, blueprint, module inventory/attachment, tuning, 병합 이력, profile unlock을 각 소유 계층에 맞게 기록한다.

#### 3.5.5 로그라이크 인과율 진행

요구의 “챕터당 미제 사건 3개”는 현 COMBAT/EVENT/BOSS **개별 노드 후보**와 단위가 다르다. 따라서 사건 하나의 case directory와 내부 노드 묶음을 나타내는 episode variant를 도입하고, 각 episode slot에 서로 다른 variant를 정확히 3개 둔다.

정본 콘텐츠 모델:

```ts
interface EpisodeVariantDefinition {
  variantId: string;
  caseDirectory: string;
  nodes: readonly RunNodeDefinition[];
}

interface EpisodeSlotDefinition {
  episodeSlotId: string;
  variants: readonly [EpisodeVariantDefinition, EpisodeVariantDefinition, EpisodeVariantDefinition];
}

interface CausalLinkDefinition {
  causalLinkId: string;
  fromBossEncounterId: string;
  rewardRelicId: string;
  targetEpisodeSlotId: string;       // source 바로 다음 episode만 허용
  forcedVariantId: string;
  targetBossEncounterId: string;
  injectHiddenEvidenceId: string;
  revealTriggerId: string;
  priority: number;
}
```

경로 선택 순서:

1. BOSS BEST completion transaction이 `unlock_causal = causalLinkId`를 읽어 link 상태를 `ACTIVE`로 만들고 `rewardRelicId`를 지급한다.
2. 이를 저장한 뒤에만 node를 진행한다. 다음 episode 진입이면 아직 결정되지 않은 slot을 resolve한다.
3. 현재 slot을 대상으로 하는 ACTIVE link가 있으면 `priority` 내림차순, 동률은 `causalLinkId` 사전순으로 하나를 선택해 `forcedVariantId`를 확정한다. 같은 slot의 비선택 link는 `SUPERSEDED`로 기록해 뒤늦게 재사용하지 않는다.
4. link가 없으면 서로 다른 3개 variant 중 episode 전용 RNG stream으로 하나를 고른다.
5. variant 결정을 저장한 다음 episode를 unlock/render한다. 이미 결정된 slot은 다시 굴리지 않는다.
6. 경로 확정 시 Relic은 제거하지 않고 link 상태만 `ROUTE_APPLIED`로 바꾼다.
7. 연결 보스에서 숨겨진 증거를 실제 사용하면 link를 `USED`로 바꿔 재사용을 막되, Relic은 수집 기록에 남긴다.

정적 causal 검증:

- `unlock_causal`은 반드시 `causalLinkId`를 참조한다.
- link의 source는 BOSS이고 target은 정확히 다음 episode slot이며, self-link/역방향/순환을 금지한다.
- `forcedVariantId`는 target slot의 3개 variant 중 하나다.
- `rewardRelicId`는 Relic catalog에 존재하고 source BOSS BEST에서만 지급 가능하다.
- target case는 `injectHiddenEvidenceId`를 `CAUSAL_HIDDEN` 상태로 정의하고 `revealTriggerId`와 target boss proof rule에서 실제 사용한다.

숨겨진 증거는 target case 정의에 없는 외부 ID를 즉석 주입하지 않는다. 선택된 target variant의 case content가 해당 evidence와 reveal trigger를 미리 정의한다. BOSS 진입 시 `ROUTE_APPLIED` link가 있을 때만 runtime inventory에 잠금 상태로 만들고, 지정 phase에서 공개한 뒤 PublicDTO에 노출한다.

증거 상태는 `CAUSAL_HIDDEN → AVAILABLE → CONSUMED`로 전이한다. AVAILABLE 증거가 포함된 첫 **유효한** Submit을 commit할 때 evidence를 CONSUMED, link를 USED로 같은 transaction에서 바꾼다. CONSUMED evidence는 Resolver가 재제출을 거부하고 PublicDTO에는 사용 완료 상태로만 표시하거나 숨긴다. Relic은 수집 기록에 남지만 gameplay evidence를 다시 생성하지 않으며, evidence/link 상태를 save한다.

저장 v4는 전체 `route_node_ids`를 미리 요구하지 않고 `resolvedEpisodeVariants`와 resolved prefix, causal link 상태를 저장한다. 구 v3의 이미 확정된 전체 `route_node_ids`는 `LEGACY_PINNED` 결정으로 변환해 기존 경로를 보존하며 중간부터 재추첨하지 않는다. active encounter의 round/hand/RNG 저장도 같은 v4에서 배선한다.

bootstrap은 canonical strip의 단일 `caseDirectory`만 preload하지 않는다. 모든 variant의 메타데이터는 시작 시 검증하되, 선택된 variant의 case definition/assets는 episode 진입 시 repository가 lazy-load하고 실패 시 진행 보드를 열기 전에 오류 화면으로 전환한다.

원자 순서는 `BOSS outcome 확정 → Relic/link 지급 → RunState 저장 → node 진행 → 다음 episode variant resolve → 결정 저장 → episode unlock`이다. 중간 상태에서 기본 seed 경로가 UI에 먼저 보이면 안 된다.

`unlock_causal`을 단순 미사용 필드로 두지 말고 boss outcome → RunState Relic/link → episode resolver → hidden evidence reveal/use까지 하나의 통합 테스트로 연결한다.

#### 3.5.6 구현 순서와 변경 경계

다음 순서는 거대한 save v4를 선행 조건으로 만들어 P0-3을 막지 않으면서도 각 단계가 독립적으로 통과하도록 자른 vertical slice다.

1. **P0-3A — identity/상태/판정 계약**: draw 정책은 아직 바꾸지 않되 `CardInstance` envelope와 `nextDrawSerial`을 먼저 도입해 중복 안전한 선택·discard 타입을 확보한다. 이어 `turnsSpent`, `SETTLE_TURN`, `AWAIT_SECURE_DECISION`, `PRESENT_PENDING_FLOW`, pending 타입, 세 frame·네 delta, Submit/decision 결과 union을 추가한다. OutcomeEvaluator의 `secureStatementRequested` boolean은 `필수 결과 → BEST 자격 → 턴 소진` directive로 분리하고 마지막 턴 우선순위 테스트를 먼저 고친다.
2. **P0-3B — Coordinator 원자화**: Submit 내부에 비용/효과/전체 손패 discard/`turnsSpent +1`/기존 modifier의 `ON_TURN_END`/flow logical commit/목표 재평가/decision 또는 terminal commit을 모은다. flow의 직접 `#startTurn()`과 public `endTurn()` 의존을 제거하고 단일 `startNextTurn()`과 typed `resolveSecureDecision()`을 추가한다. 이 단계의 draw 반환은 `readonly instanceId[]` adapter이며 정확히 5장 계약은 P0-4가 강화한다.
3. **P0-3C — 앱 수직 연결**: `createEncounterSession`은 coordinator의 pending decision을 재계산 없이 투영한다. bootstrap의 “다음 Submit에서 endTurn” 분기를 삭제하고 Secure/Continue 두 callback, Pixi rail의 최소 키보드 owner, 전체 input lock, animation barrier 뒤 autoplay decision scene을 연결한다. 접근 가능한 DOM dialog/rail 완성은 P2에서 한다.
4. **P0-3D — 안정성 게이트**: reject/예외 rollback, 일반·마지막 턴 decision 두 갈래, terminal threshold facts/우선순위, modifier·flow 1회, logical/public flow 분리, double click, 세 frame/네 delta, committed snapshot codec과 same-process remount 테스트를 통과한다. 이 단계는 브라우저 재실행 후 active encounter disk resume을 완료했다고 주장하지 않는다.
5. **P0-4 — 5장 복원추출**: 정확히 5개 draw slot·전용 `CARD_DRAW` cursor와 복원추출을 도입하고 P0-3의 유일한 `startNextTurn()` draw adapter를 교체한다. 초기/후속 hand 모두 5장, cursor +5로 결과 계약을 강화하며 v2 turn-boundary의 hand 의존 modifier를 검증·마이그레이션한다.
6. **P1 — 대질 심문**: 기본 카드 5종, active round, 라운드별 6진술·2~3방패, 방어막 판정 matrix를 연결한다.
7. **P2 — 화면 완성**: 브리핑, coffee/HP/CP 마감, gauge lifecycle, secure decision DOM dialog/inline rail, 8레이어, 명시적 판정 배너, workbench를 동기화한다.
8. **P3 — 진행/저장**: card blueprint/module 강화, save v4 active encounter 배선, 결정적 증거, episode variant/causal link, 숨겨진 증거를 순서대로 연결한다.

각 단계는 앞 단계의 타입과 테스트가 통과한 뒤 진행한다. UI는 eligibility를 다시 계산하거나 요구 수치를 하드코딩하지 않고 engine transaction/disposition을 그대로 표시해야 한다.

P0-3과 P0-4는 개발 commit은 나눠도 **하나의 production release gate**로 묶는다. `interrogationV2TurnLoop`가 꺼진 동안에는 기존 루프를 유지하고, 두 단계의 통합 테스트가 모두 통과한 뒤에만 원자 Submit+5장 복원추출을 함께 활성화한다. 따라서 P0-3 중간 adapter가 사용자에게 1장 손패 같은 반제품 동작을 노출하지 않는다.

#### B. 턴·덱·자원 엔진

- [ ] rejected Submit은 CP·자원·hand/discard·`turnsSpent/currentTurn`·machine/revision·모든 RNG cursor·로그·frame hash가 byte-identical
- [ ] 새 state/event 표의 모든 허용 전이와 금지 전이를 table test하고 8단계 매핑이 `SETTLE_TURN/AWAIT_SECURE_DECISION/PRESENT_PENDING_FLOW`를 중복 없이 정확히 한 번 포함
- [ ] resolver/modifier/objective/flow가 각각 throw하는 fault injection에서도 위 preSubmit state로 전부 rollback
- [ ] valid Submit은 INPUT/decision/terminal 모두 `turnsSpent +1`; decision action은 모두 `+0`; `currentTurn`은 `TURN_START`에서만 +1
- [ ] `multiset(discardedInstanceIds) === multiset(preSubmitHand)`이고 선택 instance의 gameplay effect/played count는 1, 나머지는 0, settlement hand는 0장
- [ ] `action/turnEnd/flowEntry/turnStartResourceDelta`가 각 before/after baseline과 정확히 같고 네 delta의 합이 preSubmit→committed 변화와 일치; 판정 배너에는 action delta만 표시
- [ ] action/ON_TURN_END가 만든 HP0·강압 한계·평정심0 fact는 후속 회복에도 유지되고 여러 fact가 생기면 HP→강압→평정심 우선순위로 reduce되며 flow/decision/draw는 실행되지 않음
- [ ] `ON_TURN_END`가 임계치를 만들면 prompt 없이 terminal이며, flow 진입 전 active set으로 정확히 1회 실행되고 새 node가 활성화한 modifier는 끝난 턴에 실행되지 않음
- [ ] node entry resource delta가 sweet spot을 만들면 decision이 열리고 Secure 후에도 delta가 보존되며, hard terminal을 만들면 decision/draw가 없음
- [ ] node claim revision/reveal 뒤 목표 재평가가 BEST 자격에 반영되고, `NO_SOLVABLE_PATH`는 flow 적용 후 최종 상태로 평가됨
- [ ] AWAIT 중 logical flow는 새 node지만 PublicDTO는 이전 presentation cursor를 유지; Continue는 효과를 재적용하지 않고 statement/cursor만 정확히 한 번 공개하며 Secure는 논리 효과만 보존하고 미공개 presentation을 폐기
- [ ] flow-entry hard/해결 불가/non-BEST final PARTIAL/Secure/final Continue의 settlement terminal은 logical effect 보존, pending=null, cursor 미전진, hand 0, draw/RNG 0의 동일 finalize 경로를 사용
- [ ] sweet-spot Submit은 `AWAIT_SECURE_DECISION`, 빈 hand, post-cost CP, 끝난 currentTurn, draw 0, `CARD_DRAW` cursor 변화 0
- [ ] typed decision Secure는 BEST이며 `ON_TURN_END`·턴 시작·CP 복원·draw를 재실행하지 않고, Continue만 잔여 턴이 있을 때 presentation→TURN_START→새 INPUT을 생성
- [ ] 마지막 턴 sweet spot은 Submit 직후 PARTIAL이 아니라 decision이며 Secure=BEST, Continue=PARTIAL; 두 branch 모두 flow 재적용/draw 0
- [ ] HP0·강압 한계·해결 불가·평정심0은 sweet spot과 동시에 발생해도 prompt 없이 문서 우선순위의 terminal이 됨
- [ ] `ON_TURN_START_PRE_DRAW` terminal은 `currentTurn = turnsSpent + 1`, CP 복원·duration tick을 commit하지만 hand 0, `CARD_DRAW` cursor +0; 상태 머신이 TURN_START→terminal을 허용
- [ ] v2 semantic validator가 turn-boundary의 `DRAW_CARD`·`DISCARD_CARD`·hand selector를 거부하고 `LOCK_CARD`는 `ON_HAND_READY`에서 기존 5장에만 적용
- [ ] 초기 조우와 일반 nonterminal 후속 턴이 같은 draw 함수로 정확히 5장을 만들고 `CARD_DRAW` cursor가 각각 정확히 +5
- [ ] 고정 seed의 전용 `CARD_DRAW` stream 5회 결과·cursor가 재현되며 중복 fixture가 실제 발생

### 4.3 수동 검증 시나리오

1. **첫 진입**: 1280×800에서 새 제목 → 진행 기록 coffee 사진 → 물컹이 심문 → 브리핑 순서와 문장 overflow를 확인한다.
2. **CP/턴**: CP 3에서 CP 2 카드를 Submit하고 resolved 상태의 실제 delta/discard 연출 뒤, 일반 상황에서는 `TURN 2`·CP full·새 중복 허용 5장이 한 번에 보이는지 확인한다. decision/terminal Submit은 `turnsSpent`만 증가하고 새 턴/손패/RNG 소비가 없어야 한다.
3. **게이지**: 평정심만 감소하는 카드, 강압만 증가하는 오답, 둘 다 변하는 카드를 각각 사용해 올바른 게이지만 흔들리는지 확인한다.
4. **방어막**: 진실 함정 공격, 유도 신문으로 거짓 방어막 파괴 → 다음 턴 같은 BROKEN 진술에 모순 지적, 파괴 전 모순 지적 거부, 증거형/비증거형 방어막 무시 카드의 오답 gate를 확인한다.
5. **스위트 스팟**: 30% 진입 Submit에서 손패가 비고 decision이 열리는지, Secure=BEST·Continue=다음 턴인지 확인한다. 마지막 턴에는 Secure=BEST·Continue=PARTIAL, 30% 초과는 decision 없음, 0%는 즉시 허위 자백이어야 하며 보스 BEST에만 결정적 증거가 지급돼야 한다.
6. **강화**: 도장 영구 적용 → 첫 전체 Run 클리어 후 포스트잇 해금과 이동 → 두 카드 클립 병합 → 두 draw slot에서 합성 카드가 뽑힘 → 저장/재개 후 상속 상태를 확인한다.
7. **인과율**: 같은 seed로 결정적 증거 Relic 유무 두 런을 만들어, 무증거는 episode variant 3개 중 랜덤·증거 보유는 전체 연계 사건 variant이며 다음 보스 phase에 숨겨진 증거가 공개되는지 확인한다.
8. **실패 경계**: 이벤트에서 HP 0, 일반 심문에서 강압 100, 보스에서 개별 한계 도달을 확인한다.
9. **도구 동기화**: production, workbench, autoplay에서 같은 카드 풀·제목·턴 의미를 사용하는지 확인한다.
